# RSK Odessa — управление строительством

Одностраничное веб-приложение (SPA) для учёта строительных объектов: сметы и график работ,
заявки на материалы и финансы, подотчёт, задачи, реестр расходов и дашборды.

**Стек:** HTML + Tailwind (CDN) + vanilla JavaScript (ES-модули), бэкенд — Supabase
(Postgres + Auth + Storage) через Cloudflare Worker-прокси. Сборки нет: файлы отдаются как есть.

## Запуск

Сборка не нужна, но `file://` не подойдёт — ES-модули работают только по HTTP.
Поднимите любой статический сервер из корня репозитория:

```bash
# вариант 1
python -m http.server 8080

# вариант 2
npx serve .
```

Затем откройте `http://localhost:8080/`.

Настройки подключения — в `js/config.js` (`CONFIG.SUPABASE_URL`, `CONFIG.SUPABASE_ANON_KEY`,
`CONFIG.STORAGE`, `CONFIG.POSITIONS`, `CONFIG.UNITS`). Anon-ключ Supabase публичный по дизайну —
данные защищаются политиками RLS на стороне БД, а не секретностью ключа.

### Обновление базы данных (миграция v2.4.0)

Приложение и база обновляются отдельно: код отдаётся статикой, а колонки в Postgres
добавляются руками. Если обновить только код, разделы начнут отвечать ошибками вида
`Не удалось сохранить счёт: Could not find the 'invoice_file_name' column of 'orders'
in the schema cache` или `column orders.payment_status does not exist` — это не баг
интерфейса, а **не применённая миграция**.

Порядок: Supabase → **SQL Editor** → вставить `database/migrate-v2.4.sql`
**целиком** → Run один раз (подробно, с самопроверкой — `database/README.md`).
Миграция добавляет в таблицу `orders` 8 колонок: `invoice_path`, `invoice_file_name`,
`invoice_uploaded_at`, `invoice_total`, `payment_status`, `delivered_at`, `paid_at`,
`paid_by_employee_id`, а также обновляет CHECK-ограничение `orders_status_check`
(старый список статусов не знает `delivered` — без этого заявка не закрывается).
Если заявка уже не закрывается, а колонки на месте (ошибка `23514`,
`violates check constraint "orders_status_check"`) — тот же шаг делает короткий
служебный файл `database/fix-orders-status-check.sql`.
Пока её нет, приложение пишет в уведомлении по-русски, чего
именно не хватает: жёлтая плашка в «📦 Снабжении» и «📊 Реестре материалов»,
красная строка в блоке «🧾 Счета на материалы», тост при сохранении
(`js/database.js` → `explainError()` — он же объясняет отказ по CHECK-ограничению).

**Если применилась только часть колонок** (SQL Editor останавливает скрипт на
первой ошибке — так и случилось на боевой базе: 4 колонки из 8): команды миграции
теперь защищены `exception`, и в конце идёт самопроверка из 8 строк `ok`/`MISSING`.
Запустите файл ещё раз целиком, посмотрите самопроверку и вкладку **Notices** —
там точная ошибка базы по каждой неудачной колонке.

**Базу нужно догнать и до v2.5.0** — файл `database/migrate-v2.5.sql` (НДС в счёте, режим цены
«цены уже с ПДВ / налог сверху», своя доставка): 12 колонок в `orders`, `order_items` и
`cash_operations`. Без них сохранение счёта отвечает «База данных не обновлена: … нет колонки
«invoice_price_mode»» — приложение называет именно этот файл. Применяется так же: SQL Editor →
файл целиком → Run. Проверить, чего базе не хватает, можно одной командой:
`node tools/checks/schema-live-check.mjs` (читает живую базу, ничего в неё не пишет и говорит,
какой файл миграции применить).

**А для архива заявок на финансы нужна ещё v2.6.0** — файл `database/migrate-v2.6.sql`. Он
**колонок не добавляет**: правит только CHECK-ограничение `cash_requests_status_check` на список
статусов (добавляет `revision` — «✏️ На доработку», и `archived` — «📥 В архив»). Без него кнопка
«📥 В архив» и возврат «✏️ На доработку» падают с
`new row for relation "cash_requests" violates check constraint "cash_requests_status_check"`
(23514), а приложение называет именно этот файл. Применяется так же: SQL Editor → файл целиком →
Run; в конце нужны шесть строк `ok`. Проверить ограничение можно только запросом в SQL Editor
(`schema-live-check.mjs` его не видит — он смотрит одни колонки), а прогнать сценарий целиком —
`node tools/checks/migration-run-check.mjs`. Подробно — `database/README.md`.


### Регистрация и вход (email + пароль)

Фронтенд намеренно простой: `signUp()` (`js/auth.js`) отправляет в Supabase только email и пароль,
после чего приложение само логинит сотрудника (`signIn()`) и показывает либо рабочие экраны, либо
«Доступ не активирован», пока Администратор не привяжет аккаунт к сотруднику (`employees.user_id`).
Писем приложение не отправляет, подтверждения по ссылке не ждёт и токенов из адресной строки
не разбирает.

Отсюда обязательное требование к проекту: **в Supabase должна быть выключена опция Confirm email**
(Authentication → Sign In / Providers → Email). Пока она включена:

* сессии после регистрации нет, поэтому вход сразу после неё падает с `Email not confirmed`
  (в форме это «Email не подтверждён. Обратитесь к администратору (Email not confirmed)»);
* каждую регистрацию Supabase сопровождает письмом-подтверждением, а у встроенной почты жёсткий
  лимит отправки: несколько регистраций подряд возвращают `429` и ошибку
  `email rate limit exceeded` — то есть новый сотрудник вообще не может зарегистрироваться.
  На вымышленные адреса вроде `fin2@rsk.com` эти письма ещё и отскакивают (bounce), и владельцу
  проекта приходит предупреждение Supabase «high rate of bounced emails» с угрозой ограничить
  отправку писем.

Свой SMTP этому приложению не нужен: подтверждение адреса ничего не защищает, реальный контроль
доступа — привязка сотрудника и политики RLS.

Supabase отвечает по-английски, поэтому самые частые отказы приложение показывает по-русски,
оставляя ответ сервера в скобках (перевод — `authErrorMessage()` в `js/auth.js`, незнакомые ошибки
выводятся как есть, без изменений):

* `Invalid login credentials` → «Неверный email или пароль (…)»;
* `Email not confirmed` → «Email не подтверждён. Обратитесь к администратору (…)»;
* `email rate limit exceeded` → «Сервер временно ограничил отправку писем. Подождите несколько
  минут и попробуйте снова (…)»;
* `User already registered` → «Такой email уже зарегистрирован — войдите на вкладке „Войти“ (…)».

**Если аккаунт уже создан, но не подтверждён** (в дашборде у него *Confirmed at: —* и
*Last signed in: —*), при включённой опции он войти не сможет. Два способа это исправить:

1. **Выключить Confirm email** — после этого вход по паролю заработает сразу;
2. **Подтвердить аккаунт вручную**: Users → строка пользователя → «…» → **Confirm email**,
   либо в SQL Editor:

```sql
update auth.users
   set email_confirmed_at = now()
 where email = 'сотрудник@rsk.com'
   and email_confirmed_at is null;
```

Готовые запросы собраны в `database/fix-unconfirmed-users.sql`: посмотреть список неподтверждённых,
подтвердить один аккаунт, подтвердить все сразу и проверить, кто ещё не привязан к сотруднику.
Колонку `confirmed_at` в `auth.users` менять нельзя — это вычисляемая колонка, Postgres откажет
в записи; подтверждение ставится в `email_confirmed_at`.

Проверка: после успешного входа в дашборде у пользователя появляются *Confirmed at* и
*Last signed in* с сегодняшней датой.

### Презентация и PDF

`Презентация.html` — самодостаточный файл: внешних библиотек нет, работает офлайн (в том числе
по `file://`, хотя остальному приложению для ES-модулей нужен HTTP). Управление: `←` `→` `↑` `↓`
`Space` `PgUp` `PgDn` — слайды, `Home` / `End` — начало и конец, `M` — оглавление (собирается из
подписей слайдов), `F` — полный экран, `Esc` — закрыть, свайпы на телефоне.

Пересохранить PDF: открыть `Презентация.html` в браузере → `Ctrl+P` → «Сохранить как PDF» →
ориентация **Альбомная**, поля **Нет**, галочка **«Фоновая графика»**. Печатная тема внутри файла
(`@page{size:A4 landscape}` + `@media print`) сама ставит один слайд на страницу, прижимает подвал
к низу листа и разворачивает тёмные слайды в светлые (иначе белый текст уходит на белый лист).
Масштаб менять не нужно — «По размеру страницы».

То же самое без диалогов, из корня репозитория (Chrome или Edge):

```powershell
& "$env:ProgramFiles\Google\Chrome\Application\chrome.exe" --headless=new `
    --no-pdf-header-footer --virtual-time-budget=6000 `
    "--print-to-pdf=$PWD\Презентация.pdf" "file:///$($PWD.Path -replace '\\','/')/Презентация.html"
```

Правило проекта: модули **не обращаются к Supabase напрямую** — только через `js/database.js`.

### Установка приложения (PWA)

Приложение ставится как обычное: значок на рабочем столе, отдельное окно без адресной строки,
оболочка берётся из кэша. Данные при этом всегда приходят из Supabase — офлайн работает только
интерфейс, не данные (см. «Ограничения»).

Что за это отвечает:

* `manifest.json` — имя, иконки 192/512 и маскабельные, цвета, `display: "standalone"`;
* `sw.js` — service worker: кэш оболочки, офлайн-навигация, кэш библиотек с CDN.
  Запросы к базе (Cloudflare Worker-прокси и `*.supabase.*`) не кэшируются никогда, иначе в
  интерфейсе остались бы устаревшие суммы;
* `js/pwa.js` — регистрация `sw.js`, карточки «Установить RSK Odessa» и «Доступна новая версия»,
  подсказка для iPhone;
* `icons/` — иконки из `logo.png`, их собирает `tools/make-icons.ps1`.

**Обязательные условия:** адрес по **https** (или `localhost`) и хотя бы один заход на сайт с
включённой сетью — после этого браузер считает приложение устанавливаемым.

Как устанавливают сотрудники:

* **Android (Chrome):** открыть адрес → меню «⋮» → **«Установить приложение»** (или «Добавить на
  главный экран»). Либо нажать «📲 Установить» в карточке, которая появляется в приложении сама.
* **iPhone / iPad (только Safari):** открыть адрес → кнопка **«Поделиться»** → **«На экран „Домой“»**
  → «Добавить». Safari не поддерживает `beforeinstallprompt`, поэтому на iOS вместо кнопки
  показывается текстовая подсказка.
* **Windows / macOS (Chrome, Edge):** значок установки в адресной строке или меню «⋮» →
  «Установить RSK Odessa»; значок появится в меню «Пуск» / Launchpad.

Карточка установки показывается только после входа (на экране авторизации она закрывала бы форму).
«✕» — больше не предлагать, «Позже» — не предлагать до конца сеанса.

Для сотрудников установка расписана пошагово, с разбором частых проблем и подсказками для
iPhone — `Документация/Инструкция-01-Установка-приложения.pdf` (см. «Инструкции для сотрудников»).

**Выпуск новой версии.** Кэш в `sw.js` называется
`rsk-odessa-v<APP_VERSION>-<SHELL_REVISION>`, поэтому порядок такой:

1. поднять `APP_VERSION` в `sw.js` (держите его равным `CONFIG.APP.VERSION` из `js/config.js`);
2. обычное открытие страницы и так идёт «сначала сеть», поэтому свежий `index.html` подхватится сам,
   а карточка «Доступна новая версия» предложит сотруднику обновиться одним нажатием
   (`SKIP_WAITING` → перезагрузка страницы);
3. кэши прошлых версий удаляются в `activate` автоматически — чистить руками ничего не нужно.

Если правка выходит **без смены версии** (исправление бага) — поднимите `SHELL_REVISION` в `sw.js`
(`r1` → `r2`). Браузер переустанавливает service worker только при изменении самого файла `sw.js`,
и только в этот момент заново скачивает файлы оболочки; иначе сотрудники с уже установленным
приложением продолжат работать на старых `js`/`css` — первый запуск после обновления отдаётся из
кэша, свежие файлы подхватываются лишь со второго.

Проверка после деплоя: открыть сайт по https → DevTools → **Application** → *Manifest*
(иконки, имя, без ошибок), *Service Workers* (activated) и *Cache Storage* —
там должен быть один кэш `rsk-odessa-v2.5.0-r5` (имя складывается из `APP_VERSION` и
`SHELL_REVISION` в `sw.js`, сейчас `2.5.0` и `r5`). Там же кнопка **«Установить»**
в адресной строке.

Пересобрать иконки (нужен только Windows PowerShell и .NET GDI+):

```powershell
powershell -ExecutionPolicy Bypass -File tools/make-icons.ps1
```

в инструкциях нужно обновлять вместе с правками `js/permissions.js`.

## Роли и права

Единственный источник правды — `js/permissions.js`:

* `ROLE_PERMISSIONS` — что может роль (Администратор, Директор, Главный инженер, Снабженец,
  Инженер ПТО, Прораб, Финансист);
* `TAB_REQUIREMENTS` — какая вкладка каким правом закрыта;
* `ROLE_UI` — урезанный интерфейс отдельной роли: какие вкладки и кнопки она не видит
  (`hiddenTabs`, `hiddenButtons` — id кнопок в шапке и внутри разделов), как называется её раздел
  (`navLabels`), в каком порядке стоят кнопки-разделы в шапке (`navOrder`, переставляет
  `applyNavOrder()` в `js/main.js`) и куда она попадает после входа (`startTab`);
* `can(action)` / `canSeeTab(tab)` / `canSeeHeaderButton(btnId)` / `getNavLabel(tab)` /
  `getNavOrder()` / `getStartTab()` / `requirePermission(action)` — проверки в коде.

**Файл сметы — только у Администратора, Главного инженера и Инженера ПТО.** Блок
«📊 Смета объекта» на вкладке «📁 Файлы» — это рабочий файл ПТО, а не документ объекта, поэтому
у остальных ролей `renderEstimateUI()` прячет его целиком, вместе с заголовком
(`#estimate-block-wrap`). Отдельное право `manage_estimate` (не путать с `manage_files` —
это документация по объекту, она осталась у той же тройки ролей): `js/modules/files.js` →
`canManageEstimate()`. Тем же правом закрыты `uploadEstimateUI()` / `uploadEstimate()` /
`viewEstimateFile()` / `downloadEstimatePDF()` — раньше `window.viewEstimateFile(id)` из
консоли отдавал подписанную ссылку на xlsx любому авторизованному. Удаление сметы
дополнительно требует `edit_project`, то есть кнопка «🗑» есть только у Администратора,
хотя смету загружает вся тройка. Плановые суммы разделов при этом по-прежнему видны
всем, кому виден объект: в «📊 План-факт», «📅 График» и в «📦 Доп. расходы».

Проверки в `js/permissions.js` — это UI-слой, а не защита. Настоящая защита сметы — RLS
в Supabase: политики на таблицу `projects` и на бакет `estimates`. Anon-ключ публичный,
поэтому подписанную ссылку на файл можно запросить и мимо приложения; если менять права
ролей, вместе с `ROLE_PERMISSIONS` нужно править и политики в БД.

**Снабженец** работает в одном окне: ему доступны только «📋 Рабочий экран» (это раздел
«Снабжение» — у этой роли он так и называется, после входа сразу открывается: `startTab: 'orders'`),
«📊 Реестр» и кнопка «💰 Финансовые запросы». Вкладки «Рабочий экран» (задачи), «Объекты»,
«Сотрудники» и «Финансы», а также кнопка «📦 Заказ материалов» в шапке у него скрыты
(`ROLE_UI['Снабженец']`) — заказ материалов он оформляет кнопкой «➕ Создать заявку» внутри
своего экрана, а свои заявки смотрит в «Мои заявки» из кабинета. Чтобы добавить или расширить
такую роль — правится только `ROLE_UI` (например, вернуть снабженцу список задач: убрать
`'tasks'` из `hiddenTabs`).

**Директор** видит все разделы (в том числе «📦 Снабжение» — следит за заявками на материалы),
но сам заявок не оформляет: у него скрыты «📦 Заказ материалов» и «💰 Финансовые запросы» в шапке
и «➕ Создать заявку» внутри раздела «💰 Финансы» (`ROLE_UI['Директор'].hiddenButtons`) — он
согласует, возвращает на доработку, отклоняет и выдаёт деньги, а не просит их себе. Это только
видимость: права (`ROLE_PERMISSIONS`) не менялись, поэтому реальное ограничение создания заявок
нужно при необходимости закреплять политиками RLS.

**Финансист** — отдельная роль для выдачи денег по уже одобренным заявкам. Его рабочий стол —
раздел заявок на финансирование: в шапке он называется «💼 Рабочий стол» (`ROLE_UI['Финансист']
→ navLabels`), после входа открывается сразу (`startTab: 'cash-requests'`), а внутри раздела
показывается панель с его подотчётом и суммой «К выдаче», а под ней — **два блока работы**:
«🧾 Счета на материалы» и «🟡 Одобренные заявки на выдачу». Что важно знать:

* финансист видит **только** `approved` (ждёт выдачи) и `issued` (уже выданные) — заявки,
  которые директор ещё не одобрил, ему не показываются (`canSeeCashRequest()` в
  `js/modules/cash-requests.js`). Вкладку закрывает право `cash_view_all`, но список
  дополнительно урезан по статусу;
* согласовывать заявки он не может: у него нет `process_cash_request`, поэтому в карточке
  нет кнопок «Одобрить / На доработку / Отклонить». Единственное действие — «💵 Выдано»
  (право `issue_cash_request`);
* ничего не создаёт: у него нет `cash_expense_self` и `create_order`, поэтому в шапке и внутри
  разделов нет «➕ Создать заявку», «📦 Заказ материалов» и «💰 Финансовые запросы»;
* помимо своего экрана ему доступны «📊 Реестр», «🏗 Объекты» и «👥 Сотрудники»; вкладки задач
  и снабжения скрыты (`ROLE_UI['Финансист'].hiddenTabs`). В шапке «💼 Рабочий стол» стоит
  **первым** — это его рабочее место (`ROLE_UI['Финансист'].navOrder`, порядок расставляет
  `applyNavOrder()` в `js/main.js`), у остальных ролей порядок кнопок прежний, как в разметке;
* панель над списком заявок показывает «💰 Мой баланс» (его подотчёт) и «🟡 К выдаче» — сумму по
  одобренным заявкам (`renderFinancierPanel()` в `js/modules/cash-requests.js`). Обе цифры
  читаются из того же представления `employee_cash_balance`, что и баланс в кабинете;
* рабочий стол собран в **один блок «💰 Финансовые заявки»** (`#financier-desk-block`, заголовок —
  `#financier-desk-head`, рисует `renderFinancierDeskHead()` в `js/modules/cash-requests.js`;
  виден только финансисту, у остальных ролей — как раньше). Внутри блока две рабочие очереди, и у
  каждой своё меню:
  * «🧾 Счета на материалы» (`#material-invoices-panel`, рисует `js/modules/invoices.js` — счета
    снабжения, оплата безналом фирмы). Меню «⏳ Ожидают оплату (N) / ✅ Оплаченные (M)» рисует
    `renderInvoiceHead()`, переключает списки `setInvoiceView()` (`window.setInvoiceView`). У истории
    оплат есть фильтр периода «📅 Всё время / Этот месяц / Прошлый месяц» (`setInvoicePeriod()`) и
    выгрузка в Excel **по этому фильтру**: `exportMaterialInvoicesToExcel()` выгружает ровно то, что
    видно на экране (активное меню + период) — с шапкой, автофильтром и суммами числами. У очереди
    долгов фильтра нет: неоплаченный счёт должен быть виден целиком, а не прятаться по дате;
  * «🟡 Одобренные заявки на выдачу» (`#financier-approved-block`): заголовок блока и переключатель
    «🟡 К выдаче (N) / 🟢 Выданные (M)» собирает `renderFinancierApprovedHead()`, переключает список
    `setFinancierView()` (`window.setFinancierView`);
  * общие фильтры раздела (`#cashreq-filters`) финансисту прячет `applyFinancierDesktopLayout()` —
    у директора, администратора и кассиров лента заявок с фильтрами осталась прежней (их фильтр
    `currentFilter` эти функции не трогают) и рендерится в тот же общий контейнер
    `#cash-requests-container`;
* **подотчёт финансиста пополняет директор** — кнопка «💼 Пополнить баланс финансиста» в разделе
  «💰 Финансы» (`js/modules/cash.js` → `openTopUpBalanceModal()` / `saveTopUpBalance()`).
  Кнопка показывается всем, у кого есть право `cash_issue` (Директор, Администратор,
  Главный инженер), и создаёт одну операцию `issue` **без привязки к объекту**. Если сотрудника
  с должностью «Финансист» ещё нет, окно подскажет добавить его в разделе «Сотрудники»
  (должность уже есть в `CONFIG.POSITIONS`). Рядом с кнопкой виден **актуальный баланс
  финансиста** (`renderFinancierBalanceHint()`): цифра перечитывается при каждом открытии
  раздела и сразу после пополнения, поэтому сумму не нужно выяснять звонком. Самим финансистам
  и прорабам подсказка не показывается — она закрыта тем же правом `cash_issue`.

**Постановка задачи из карточки сотрудника** — отдельное право `assign_task_to_employee`
(Администратор, Директор, Главный инженер). Кнопка «➕ Поставить задачу» показывается, только если
у роли есть и `create_task`, и `assign_task_to_employee`, а сотрудник не заблокирован. Баланс
подотчёта в карточке виден кассиру (`cash_view_all`) или самому сотруднику.

UI скрывает недоступные кнопки, но это только удобство: настоящая защита — политики RLS в Postgres.
Список должностей для форм — `CONFIG.POSITIONS`, он должен совпадать с ключами `ROLE_PERMISSIONS`,
иначе роль получит доступ «по минимуму» (в консоль пишется предупреждение).

## Важные инварианты

* **Номера заявок** (`З-…` для материалов, `Ф-…` для финансов) считаются как «максимум за год + 1»
  (`db.getNextRequestNumber()` и `generateCashRequestNumber()`), а не через `COUNT(*)`, и при коллизии
  (ошибка Postgres `23505`) запрос повторяется. `COUNT` ломается при удалении заявок и в параллельных сессиях.
* **Повторная загрузка сметы** не пересоздаёт разделы: строки сопоставляются по нормализованному имени
  (`normalizeSectionName()`), обновляются только план-суммы, а `planned_start_date` / `planned_end_date` /
  `actual_end_date`, проставленные в графике, сохраняются. Удаляются лишь разделы, которых больше нет в файле.
  Служебный раздел «Доп. расходы» из сопоставления и удаления исключён (`isExtraSectionName()`): если такое
  имя случайно встретится в Excel-файле, строка пропускается с предупреждением в консоли.
* **«📦 Доп. расходы» — подвкладка карточки объекта (сразу после «📊 План-факт»).** Работы и материалы,
  которых нет в смете, привязываются к объекту через служебный раздел `sections.name = 'Доп. расходы'`
  (`CONFIG.EXTRA_SECTION.NAME`): он создаётся лениво при первом обращении к списку разделов
  (`js/modules/sections.js` → `loadSectionsWithExtra()`) и один на объект. Что важно знать:
  * в селектах «Раздел» он идёт **отдельной группой** «⚠ Вне сметы» и янтарным цветом
    (`buildSectionOptionsHtml()`), поэтому его нельзя перепутать с разделами сметы. Селекты форм заказа
    материалов, финансового запроса и расхода перерисовывает `fillSectionsSelect()` — раньше каждый модуль
    строил список сам, и до появления служебного раздела у объекта без сметы было нечего выбрать
    («загрузи смету»), из-за чего заказ/расход было невозможно создать;
  * `loadSections()` (estimate.js) и график возвращают **только сметные** разделы, а
    `loadExpensesForProject()` (cash.js) отдаёт траты вне сметы отдельным массивом `extraOps` — поэтому
    в план-факте, графике и рейтинге перерасхода на дашборде он не появляется, а собирается на подвкладке
    (`js/modules/extra-costs.js`) двумя списками — «🛠 Работы» и «📦 Материалы» (доставка считается
    материалом, как в план-факте; «📋 Прочее» — только если такие траты есть). Суммы списков совпадают
    с карточками сводки: и блоки, и итог считаются из одного массива `extraOps`
    (`splitExtraOperations()` + `calcExtraTotals()`);
  * **одна заявка ≠ два расхода.** Позиции заявки с оплатой фирмой приходят в `extraOps`
    «псевдо-операциями» (cash.js → `_source: 'order'`), поэтому закрытая заявка показывалась дважды:
    строками в блоке «Расходы подотчёта» и ещё раз в таблице «Заказы материалов». Теперь закрытая заявка
    выводится **только** в списках «Работы»/«Материалы», а таблица «⏳ Заявки вне сметы в работе» оставлена
    для незакрытых заявок (`new` / `in_progress`) — они в «Итого вне сметы» не входят, пока не закрыты.
    Двойного счёта не было и нет: строки `extraOps` дизъюнктны (`cash_operations` для заявки создаются
    только при `payment_source = 'employee'`, псевдо-операции — только при `'company'`);
  * **подробности записи — окно `#extra-cost-detail-modal`** (index.html). Клик по строке списка вызывает
    `window.__openExtraCostDetail(id)`, клик по заявке в работе — `window.__openExtraOrderDetail(orderId)`,
    рендер — `showExtraCostDetail()`. В окне: источник («🏢 заявка · оплата фирмой», «💵 заявка · из
    подотчёта», «🧾 расход кассы / подотчёта»), сотрудник, дата, поставщик, статус и способ оплаты заявки,
    позиции записи, а при много-позиционной заявке ещё и «📋 Заявка целиком»; кнопки — «📎 Открыть чек»
    (`window.viewReceipt`) и «📦 Открыть карточку заявки» (динамический импорт `orders.js`, кнопка есть
    только при `canSeeTab('orders')`). Данные для окна берёт состояние модуля `extraState`, которое
    заполняет `renderExtraCostsUI()`; позиции заявок раздела грузятся одним запросом `order_id.in`;
  * показывается **только то, что попало в реестр** — позиции закрытых заявок материалов и траты из
    авансового отчёта/кассы. Блок «💰 Финансовые запросы» из подвкладки убран: выданные в подотчёт
    деньги — ещё не трата, они никогда не входили в «Итого вне сметы», а сами запросы живут в разделе
    «💰 Финансы». Потраченная сумма появится строкой в «Работах» / «Материалах» после авансового отчёта
    (`db.select('cash_requests')` на подвкладке больше не выполняется вообще);
  * в «📊 Финансы по объекту» доп. расходы видны отдельной янтарной строкой, а «💰 ИТОГО по смете»
    остаётся сравнением план/факт по смете (перерасход считается только по смете); строкой ниже
    «🧾 Всего с доп. расходами» показывает тот же план и факт/остаток уже вместе с ними, а если из-за
    доп. расходов объект ушёл в минус, вместо «✔ В норме» в шапке горит
    «⚠️ Смета ушла в минус из-за доп. расходов» (иначе «в норме» противоречило бы минусу ниже);
  * при удалении сметы раздел **не удаляется** (`db.remove('sections', { project_id, 'name.neq': … })`),
    иначе расходы и заявки вне сметы остались бы без раздела; при удалении объекта разделы удаляются все,
    включая служебный;
  * имя раздела — ключ сопоставления: переименовывать его в БД нельзя (см. `js/config.js`).
    В селекте служебный вариант помечен `data-extra-section="1"` — так формы отличают его от сметных
    разделов, не полагаясь на текст подписи;
  * **миграции не нужны:** новых таблиц и колонок нет, всё живёт в существующих `sections`, `orders`,
    `cash_requests`, `cash_operations`. Требуются только права на вставку строк в `sections` — они уже
    есть, потому что разделы создаёт загрузка сметы (`js/modules/estimate.js`);
  * итоги подвкладки считает чистая функция `calcExtraTotals()` (материалы включают доставку — как в
    план-факте), рендер — `renderExtraCostsUI()` в контейнер `#proj-subtab-extra`.
* **Блок сметы (`#estimate-block` → `renderEstimateUI()`) живёт только на подвкладке «📁 Файлы»** карточки
  объекта, рядом с «📁 Документация по объекту». На подвкладке «📊 План-факт» его держать нельзя: её
  содержимое целиком перезаписывает `renderSectionsUI()` через `innerHTML`, и любой статичный контент там
  (включая кнопку загрузки сметы) стирается сразу после открытия карточки. `switchProjectSubTab('files')`
  перерисовывает блок при каждом входе на подвкладку. Виден он только Администратору, Главному
  инженеру и Инженеру ПТО (`manage_estimate`): остальным ролям прячется вся обёртка
  `#estimate-block-wrap` вместе с заголовком «📊 Смета объекта».
* **Подвкладка карточки объекта** — второй аргумент: `openProjectDetail(id, 'files')`. Так после
  загрузки/удаления сметы пользователь остаётся на «📁 Файлы», а не выбрасывается на «Общая информация».
* **На кнопках навигации счётчиков нет**: `#tasks-badge`, `#projects-badge`, `#employees-badge`,
  `#orders-badge`, `#cash-requests-badge` и функции `updateTasksBadge()` / `updateProjectsBadge()` /
  `updateEmployeesBadge()` / `updateOrdersBadge()` удалены, из подписей убраны «(N)». Причина: разделы
  грузятся лениво, поэтому до первого открытия вкладки счётчики показывали `0` и вводили в
  заблуждение. `updateCashRequestsNavButton()` (`js/modules/cash-requests.js`) по-прежнему показывает
  или скрывает кнопку «💰 Финансы» по правам (через `canSeeTab`), но цифру не выводит.
* **Удаление объекта** идёт каскадом вручную (`confirmDeleteProject`): сначала файлы в Storage,
  затем позиции заявок, потом заявки/задачи/расходы/разделы и только после этого сам объект.
  Не полагайтесь только на `ON DELETE CASCADE` — его может не быть в БД.
* **Загрузка данных ленивая**: на старте грузятся только задачи (нужны для личного дашборда
  сотрудника), остальные разделы подтягивает `switchTab()` при первом открытии вкладки.
* **Нельзя опираться на кэш, который наполняется лениво.** Была ошибка: формы «🛒 Внести расход» и
  «↩️ Возврат» из «💰 Авансового отчёта» искали сотрудника через глобальный `window.__getEmployeeById`,
  а тот появлялся только после `loadEmployees()` (вызывается лишь из `switchTab('employees')`).
  В итоге у пользователя, который ни разу не открывал вкладку «👥 Сотрудники» (например, у прораба),
  по кнопке вылетало «Сотрудник не найден». Теперь формы берут привязанного сотрудника из
  `getEmployee()` (`js/permissions.js`) — он загружается при входе в приложение. Мостик
  `window.__getEmployeeById` удалён как ненужный.
* **Карточка сотрудника открывается мгновенно, данные докидываются следом.** Статичная часть
  (ФИО, должность, контакты, кнопки блокировки) рисуется сразу, а блоки «🏗 Объекты, которые ведёт: N»,
  «💰 Баланс подотчёта» и «🎯 Актуальные задачи: N» заполняет `refreshEmployeeCardExtra()`
  (`js/modules/employees.js`) в контейнер `#employee-card-extra` — карточка не «залипает» на ожидании
  запросов, а ошибки чтения просто оставляют блоки пустыми.
* **В карточке сотрудника видны только актуальные задачи** (`pending` / `in_progress`) и только те,
  что проходит та же проверка, что `canSeeTask()` в `js/modules/tasks.js`: Админ/Директор
  (`view_all_tasks`) видят все задачи сотрудника, остальные — где они автор или исполнитель
  (поэтому Главный инженер и Прораб увидят в чужой карточке лишь поставленные ими задачи).
  Объекты — это `projects.foreman_id = emp.id`. Клик по объекту уходит в его карточку
  (`window.openProjectFromEmployeeCard` → `openProjectDetail`), клик по задаче — в карточку задачи
  (`window.openTaskFromCard`, при пустом кэше сначала `loadTasks()`).
* **«➕ Поставить задачу» из карточки сотрудника доводит исполнителя до формы**:
  `openNewTaskForm(presetAssigneeId)` после загрузки списка исполнителей подставляет сотрудника
  (`presetAssigneeOption()`), а если его должности нет в списке — добавляет отдельный пункт, чтобы
  не было тупика «сотрудника нет в списке». После успешного `saveNewTask()` вызывается
  `window.refreshEmployeeCardExtra()` и блок задач в открытой карточке обновляется.
* **Фильтрация — на стороне БД** (`id.in`, `section_id.in`, `status.in`, `operation_type`), а не выкачиванием
  всей таблицы в браузер.
* Деньги считаются через `roundMoney()` из `js/utils.js` — не «сырой» арифметикой с плавающей точкой.
* **Экспорт реестра в Excel** (`exportRegistryToExcel()`, `js/modules/registry.js`) настраивает лист явно:
  `worksheet['!cols']` — ширина каждой колонки по самому длинному значению (потолок 250 символов, у Excel
  предел 255), шапка получает автофильтр, «Дата» пишется настоящей датой Excel со **встроенным** форматом
  (в русской локали отображается как `14.08.2026`, поэтому сортировка по дате не ломается), деньги — встроенным
  `#,##0.00`. Без `!cols` Excel открывает файл с одинаковыми узкими колонками и текст в ячейках не читается.
  Кастомные форматы (`z` вида `dd.mm.yyyy`, `#,##0.###`) сознательно не используются: SheetJS CE 0.18.5
  присваивает им `numFmtId < 164`, а такие определения Excel может проигнорировать.
* **«💰 Авансовый отчёт» фильтруется в браузере** (`js/modules/cash.js`): грузятся последние
  `MY_OPERATIONS_LIMIT` (500) операций сотрудника, дальше — объект (включая `MY_OPS_NO_PROJECT` —
  «— Без объекта —» для расходов без объекта) и период «Дата с / Дата по»
  (`applyMyOperationsFilters()`, сброс — `resetMyOperationsFilters()`). Дата операции — `YYYY-MM-DD`,
  сравнивается со значением `input[type=date]` как строка, поэтому часовые пояса не мешают.
  Активные фильтры хранятся в состоянии модуля, а не в DOM: контейнер `#my-operations-content`
  перерисовывается целиком после «Внести расход», возврата и повторного открытия, иначе выбор
  пользователя терялся бы. Перерисовывается отдельно только список (`#my-ops-list`). В шапке видно
  «Показано: N из M» с приходом/расходом по фильтру (приход — выдача подотчёта и корректировка,
  расход — расход и возврат, знаки как в списке).
* **«📥 Excel» в авансовом отчёте выгружает только отфильтрованные операции**
  (`exportMyOperationsToExcel()`): расход разворачивается в строку на позицию (иначе не видно, из чего
  сложилась сумма), дата пишется настоящей датой Excel, деньги — числами с встроенным форматом
  `#,##0.00`, ширины `!cols` считаются по отображаемому виду (дата `14.08.2026`, деньги `40 000,00`,
  а не сырое `40000`), под таблицей добавляются «Итого приход / Итого расход / Баланс», а автофильтр
  накрывает только строки операций. Имя файла собирается через `sanitizeFileName()`, поэтому кириллица
  транслитерируется. Закрепление области не используется: SheetJS CE 0.18.5 его не пишет.
* **Названия в интерфейсе и в коде расходятся.** Вкладка раздела заявок на подотчёт называется
  «💰 Финансы» (у роли «Финансист» — «💼 Рабочий стол», см. `ROLE_UI.navLabels`), кнопки создания —
  «💰 Финансовые запросы» (`#btn-new-cash-request`) и «📦 Заказ материалов»
  (`#btn-new-order`). В коде и БД сущности по-прежнему `cash_requests` / `orders`, а номера заявок — «Ф-N/YY»
  и «З-N/YY». При поиске по подписям учитывайте и старые формулировки «заявка», «заявки финансов».
* **Кнопка сохранения возвращается в рабочее состояние при любом исходе.** В формах заявок
  (`saveNewCashRequest` / `createCashRequest`, `saveNewOrder` / `createOrder`, `closeOrder`) сборка
  данных вынесена в отдельную функцию, а сохранение обёрнуто в `try / catch / finally`:
  после успеха кнопка снова доступна и подписана («💾 Создать заявку»), а исключение показывается
  красной плашкой. Раньше после успешного сохранения кнопка оставалась «Сохраняем...» и выключенной,
  и следующая попытка молча не отправлялась — форма выглядела зависшей, а заявка не создавалась.
  Там же проверяется, что база вернула созданную запись: пустой ответ (без тела) давал бы `TypeError`
  на `data.id` вместо понятного сообщения.
* **Список заявок на материалы открывается только у тех, кому он виден** (`canSeeTab('orders')`):
  у прораба вкладка «Снабжение» скрыта (право `create_order` есть, `view_orders_tab` — нет),
  а прямой `switchTab('orders')` показывал ему «Недостаточно прав» сразу после успешного сохранения.
* **Заявка на финансы идёт по цепочке «прораб → директор → финансист».** Статусы: `pending`
  (ждёт решения директора) → `approved` (одобрена, ждёт выдачи) → `issued` (деньги выданы),
  с ветками `revision` (директор вернул автору с причиной) и `rejected` (директор отказал).
  В карточке заявки директор видит три кнопки — «✅ Одобрить», «✏️ На доработку», «❌ Отклонить»;
  для возврата и отказа причина обязательна, иначе действие не выполняется
  (`requestRevisionCashRequest()` / `rejectCashRequest()`). Доработанная заявка снова становится
  `pending` (номер не меняется, позиции перезаписываются — `updateCashRequest()`), а решение
  директора и причина стираются: они относились к прошлому кругу.
  * новой колонки под причину возврата нет намеренно: причина пишется в существующую
    `rejection_reason`, а что в ней лежит — видно по статусу заявки. Так обновление не требует
    миграции боевой базы (новое значение статуса пишется в тот же `text`);
  * `revision` входит в фильтр «🔄 Активные» и имеет отдельную кнопку «✏️ На доработке»;
  * удалить заявку автор может, пока директор её не обработал: в статусах `pending` и `revision`.
* **Рабочий экран прораба показывает его заявки — с фильтрами по стадиям.** Оба блока
  (`renderMyCashRequests()` и `renderMyMaterialOrders()` в `js/modules/dashboard.js`) рисует одна
  функция-каркас `renderDashboardBlock()`, а над списком стоит ряд кнопок-фильтров
  (`renderBlockFilters()`):
  * 💰 **«Мои заявки на финансирование»** — «📋 Все / ⏳ Поданы / 🟡 Одобрены / ✏️ На пересмотр /
    ❌ Отклонены / 🟢 Выданы». В «Все» порядок прежний: сначала то, что требует внимания —
    «✏️ Требует доработки» с причиной директора и кнопкой «✏️ Исправить и отправить», затем
    одобренные («деньги выдаёт финансист»), ожидающие решения, а история — последние пять
    отклонённых и выданных (`CASH_REQUEST_ALL_LIMITS`). В фильтре статуса видно **все** заявки
    этого статуса: раньше отклонённая заявка не показывалась на экране вообще, теперь она в
    «❌ Отклонены» вместе с причиной отказа директора;
  * 📦 **«Мои заявки на материалы»** — «📋 Все / 📤 Поданы в снабжение (`new` + `in_progress`) /
    🚚 Доставлено на объект (`delivered`)»: прораб сразу видит, что уже заказано, а что привезли
    (`matchesMaterialFilter()`). «Все» оставлено прежним — заявки в работе плюс последние пять
    закрытых/архивных;
  * 📦 **карточка заявки на материалы — без суммы и кликабельна целиком.** Список отвечает на
    вопрос «что заказано и что привезли», а не «сколько это стоило»: цену вносит снабженец при
    доставке вместе с поставщиком и счётом, поэтому в строке остаются только номер, статус,
    объект с разделом, поставщик и дата, а справа — подсказка «Подробнее ›». Нажатие на **любое
    место карточки** (`renderMyMaterialOrdersBody()`) открывает общую подробную карточку заявки
    `openOrderDetail()` из «Снабжения» (состав с количествами и ценами, объект и раздел,
    поставщик, даты, отметка об оплате счёта). Раньше кликабельным был только номер в маленькой
    кнопке, а сумма дублировалась в списке;
  * фильтры **не ходят в базу**: данные последнего рендера лежат в `blockCashRequests` /
    `blockOrders` / `blockProjects`, а нажатие кнопки перерисовывает только содержимое блока
    (`dash-block-finance-body` / `dash-block-materials-body`) — экран не мигает, а состояние
    «Скрыть» не сбрасывается (`toggleDashboardBlock()` прячет тот же контейнер);
  * блок заявок на финансирование наполняется из кэша модуля заявок (`loadCashRequests()` +
    `getCashRequestsCache()`), поэтому карточка открывается тем же окном, что и в разделе
    «💰 Финансы» — иначе было бы «Заявка не найдена». После создания, доработки или удаления заявки
    дашборд перерисовывается сам (`refreshDashboardIfVisible()`), но только если он открыт
    (`AppState.currentTab === 'tasks'`).
* **«💵 Выдано» у финансиста списывает деньги с его подотчёта.** Выдача создаёт две операции:
  `issue` получателю (его подотчёт растёт — как было и раньше) и `return` финансисту (его подотчёт
  уменьшается). Тип `return` выбран потому, что представление `employee_cash_balance` понимает только
  `issue / expense / return`, а `expense` попал бы в «📊 Реестр» как настоящая трата — хотя выданный
  подотчёт тратой ещё не является (она появится после авансового отчёта получателя). Отдельный тип
  `transfer` потребовал бы правки представления в боевой базе. Перед выдачей финансист видит остаток
  своего подотчёта, а если суммы не хватает — предупреждение, что баланс уйдёт в минус (долг).
  Выдавать по одобренной заявке могут и кассиры (Администратор, Директор, Главный инженер): у них
  кнопка называется «💵 Выдать» и ничей подотчёт не уменьшает.
* **Баланс финансиста в разделе «💰 Финансы» — та же цифра, что в карточке сотрудника.**
  Подсказка `#financier-balance-hint` рядом с кнопкой пополнения наполняется
  `renderFinancierBalanceHint()` (`js/modules/cash.js`) из представления `employee_cash_balance`
  и перечитывается при каждом открытии раздела и сразу после пополнения — своего кэша у неё нет,
  поэтому «отстать» от базы она не может. Если сотрудника с должностью «Финансист» в базе нет,
  вместо суммы выводится «💰 Финансиста нет в штате»: директор сразу видит, почему кнопка не
  предлагает получателя.
* **Порядок кнопок в шапке меняется только в DOM, разметка остаётся общей.** `applyNavOrder()`
  (`js/main.js`) по `ROLE_UI.<роль>.navOrder` вставляет кнопки-разделы перед первым элементом
  шапки, который разделом не является, поэтому кнопки-действия («📦 Заказ материалов»,
  «💰 Финансовые запросы») и меню кабинета остаются справа на своих местах. Сейчас `navOrder`
  есть только у «Финансиста» — у остальных ролей порядок такой же, как в `index.html`.
* **Закупка материалов идёт по цепочке «счёт поставщика → доставка на объект → реестр → оплата».**
  Снабженец создаёт заявку (`new` → `in_progress`), затем кнопкой «🧾 Счёт от поставщика»
  (`openOrderInvoiceModal()` / `saveOrderInvoice()`) загружает файл счёта, указывает поставщика и
  цены по позициям; кнопкой «🚚 Доставлено на объект» (`closeOrder()` с `delivered`) закрывает
  закупку. Позиции сразу попадают в «📊 Реестр материалов», а счёт уходит в очередь финансиста
  «🧾 Счета на материалы» (`js/modules/invoices.js`, карточка счёта открывает окно подробностей),
  где тот отмечает его оплаченным (`markMaterialInvoicePaid()`).
  * **доставка водится отдельным блоком счёта, и её вид выбирает снабженец.** В окне «🧾 Счёт от
    поставщика» есть блок «🚚 Чья доставка» (`index.html` → радиокнопки
    `input[name="order-invoice-delivery-type"]`) и поле «🚚 Стоимость доставки (грн)»
    (`#order-invoice-delivery`). Сумма сохраняется **отдельной позицией заявки** — строкой
    `order_items` с именем `CONFIG.DELIVERY_ITEM.NAME` («Доставка», `qty = 1`, эмодзи 🚚 рисует
    интерфейс) или `COMPANY_NAME` («Доставка компании»), а не ценой материала. Вид доставки тоже
    хранится в имени строки, поэтому отдельной колонки (и миграции базы) не нужно. Пустое поле
    удаляет строку, повторное сохранение обновляет её, а смена вида переименовывает ту же строку —
    строка одна на заявку (`saveOrderInvoice()` → `saveDeliveryItem()`). Если сумму не вписывали,
    строки нет — при следующем открытии окно снова предложит «доставку поставщика»: на деньги это не
    влияет, пустая доставка не входит ни в счёт, ни в заявку. В окне «🚚 Доставлено на
    объект» она видна отдельной строкой с иконкой 🚚, где указывают фактическую сумму. Итог заявки
    (`orders.total_sum`) всегда включает доставку, а счёт (`orders.invoice_total`) — по виду:
    * «🏬 Доставка поставщика» — везёт поставщик: сумма входит в счёт, финансист платит её вместе
      с материалами (`invoice_total = total_sum`);
    * «🏢 Доставка компании» — везёт компания: поставщик её не выставляет, поэтому `invoice_total`
      — только материалы (финансист оплачивает ровно счёт поставщика), а строка доставки остаётся
      расходом заявки. В окне счёта под итогом появляется подсказка «Вне счёта поставщика: …»;
  * **в реестре доставка — своя категория.** `js/modules/registry.js` помечает позицию доставки
    категорией `delivery` (`isDeliveryItem()` / `getDeliveryItemType()` из `js/utils.js` — сравнение
    по имени, как у служебного раздела), поэтому фильтр «Категория → 🚚 Доставка» находит реальные
    суммы доставки и в безналичных заявках, и в заявках из подотчёта (там позиции приходят из
    `cash_operations.items`). У строки «Доставка компании» в колонке «Оплата» стоит «🏢 Вне счёта»
    (в выгрузке Excel — «Вне счёта поставщика»), а не «Ожидает оплаты»: долга перед поставщиком по
    ней нет. В план-факте и в «Доп. расходах» доставка по-прежнему считается материалом — как и для
    расходов кассы с `category = 'delivery'` (`cash.js`, `calcExtraTotals()`);
  * **материалы приезжают раньше денег:** заявка доходит до `delivered` и попадает в реестр при
    `payment_status = 'debt'` (в интерфейсе — «Ожидает оплаты»). Единственные статусы реестра —
    `delivered`, `closed`, `archived`, поэтому «нет денег» больше не задерживает материалы на
    складе в учёте;
  * **признак оплаты — `orders.paid_at`, а не `payment_status`.** Снабженец может перезагрузить счёт
    уже после оплаты (исправил цены, приложил читаемое фото) — при этом `payment_status` снова
    станет `debt`, а `paid_at` останется, и позиции не «откатятся» в «Ожидает оплаты».
    `payment_status` — витрина для фильтров, бейджей и очереди счетов, все решения по деньгам
    принимаются по `paid_at`;
  * **бейдж оплаты описывает заявку, а не отдельную позицию, и появляется только когда статус
    известен.** Его считает `orderPaymentState()` в `js/modules/orders.js`: `paid_at` → «Оплачено»,
    `payment_status`/позиции `debt` → «Ожидает оплаты», а если ни счёта, ни доставки ещё нет —
    бейджа нет вовсе. Раньше `createOrder()` писала позициям `payment_status = 'paid'`, и заявка,
    которую не брали в работу, выглядела оплаченной; теперь позиции создаются без статуса оплаты
    (его ставит доставка или финансист). В окне «🚚 Доставлено на объект» строки подписывает
    `updateCloseOrderPaymentHints()` — по выбору «кто платит» (фирма → «Ожидает оплаты», подотчёт
    снабженца → «Оплачено»). Статичного текста «Ожидает оплаты / Оплачено» в окне больше нет:
    он читался как «позиции уже оплачены»;
  * **оплата счёта — безнал фирмы:** `markMaterialInvoicePaid()` не создаёт операций подотчёта (ни у
    финансиста, ни у снабженца) и не меняет `employee_cash_balance`. Наличную закупку из подотчёта
    закрывает прежний путь: `payment_source = 'employee'` + расход `expense` при закрытии заявки;
  * файл счёта кладётся в бакет чеков в подпапку `invoices/` (`CONFIG.STORAGE.INVOICES_BUCKET`,
    по умолчанию `receipts`) — отдельный бакет и отдельная политика Storage не нужны;
    `invoice_path` хранит путь в бакете, `invoice_total` — сумму по счёту (её видит финансист);
  * **в списке — статус, оплата — в окне подробностей.** Карточка очереди целиком кликабельна
    (`renderInvoiceCard()` → `openMaterialInvoiceDetail()`), справа внизу стоит «⏳ Ожидает оплату»,
    а кнопка «✅ Оплачено» живёт в окне (`#material-invoice-detail-modal`, рисуют
    `renderInvoiceDetail()` и `renderInvoiceDetailActions()`). Раньше кнопка стояла прямо в
    карточке очереди, и список «⏳ Ожидают оплату» читался как «эти счета уже оплачены». Окно
    одно для очереди и истории (у оплаченного счёта кнопки оплаты нет) и показывает суммы по счёту
    и по заявке — когда они разные, видно, что своя доставка в счёт поставщика не вошла, — даты
    (счёт загружен, заявка создана, желаемая поставка, доставлено), файл счёта и отметку
    «кто и когда оплатил»;
  * право на оплату — `pay_material_invoice` (Финансист, Директор). Блок перерисовывает
    `renderMaterialInvoices()` (при открытии раздела читает **два** списка: очередь
    `payment_status = 'debt'` и историю `'paid'` с датой и тем, кто оплатил), её вызывает
    `loadCashRequests()` — поэтому блок виден и на рабочем столе финансиста, и в разделе
    «💰 Финансы» у директора. Смена меню и фильтра периода идёт без запросов к базе:
    `setInvoiceView()` / `setInvoicePeriod()` перерисовывают кэш (`paintMaterialInvoices()`).
    В истории оплат показываются только строки со счётом: миграция перевела в `'paid'` и старые
    заявки без счёта вовсе — им в истории делать нечего;
  * изменения базы собраны в `database/migrate-v2.4.sql` (8 колонок в `orders` + перевод старых
    заявок в `payment_status = 'paid'`, чтобы они не попали в очередь счетов). Миграция **обязана**
    трогать и CHECK-ограничение `orders_status_check`: на боевой базе список статусов остался от
    прежних версий, без `delivered`, и закрытие закупки падало с
    `new row for relation "orders" violates check constraint "orders_status_check"` (23514).
    БЛОК 4 файла снимает старое ограничение и ставит новое —
    `status in ('new', 'in_progress', 'delivered', 'closed', 'archived')` (список — `CONFIG.ORDER_STATUS`).
    Без этой миграции счёт, доставка и оплата не сохраняются: PostgREST отвечает «Could not find
    the 'delivered_at' column…», а приложение переводит такую ошибку в инструкцию
    (`db.explainError()` — он же разбирает отказ по CHECK-ограничению) и показывает плашку в
    «📊 Реестре материалов». Порядок применения — `database/README.md`, раздел 9 инструкции
    Администратора.
* **Ведомость пополнений подотчёта финансиста** — кнопка «📄 Ведомость пополнений» в разделе
  «💰 Финансы» (`openFinancierTopUpStatement()` в `js/modules/cash.js`, у финансиста — «📄 Ведомость
  пополнений от директора»): построчный список передач денег в подотчёт (дата, кто передал, сумма,
  комментарий), итоги «Всего пополнено / Пополнений» и выгрузка в Excel
  (`exportFinancierTopUpStatement()`).
  * пополнение помечается маркером `cash_operations.source = 'financier_topup'`
    (`saveTopUpBalance()` → `addIssue()`), поэтому ведомость не путает пополнения с обычными
    выдачами подотчёта (`manual`) и расходами из заявок (`order`);
  * строки, созданные до v2.4.0, распознаются по описанию («Передал…») — сразу после обновления
    ведомость показывает историю, а не пустой экран.
* **Язык и цветовая схема — персональные настройки устройства** (окно «⚙ Настройки» в меню кабинета:
  `js/settings.js`, `js/theme.js`, `js/i18n.js`, `css/theme.css`). Выбор хранится в `localStorage`
  (`rsk.lang`, `rsk.theme`), применяется до первой отрисовки (`initI18n()` / `initTheme()` в
  `js/main.js`) и не затрагивает других сотрудников.
  * язык: RU и UK. Текст берётся из двух словарей `js/i18n.js`: `DICT` — по ключам
    (`data-i18n="..."` в `index.html` и `i18n.t('ключ')` в новых модулях), `PHRASES` — пары
    «русская фраза → украинская» для старых модулей, которые пишут подписи прямо в коде: перевод
    подставляется в готовый DOM, поэтому переписывать их на `t()` не нужно. Пары применяются от
    длинных фраз к коротким («Мои заявки на финансирование» переведётся раньше, чем «Мои заявки»),
    `translateText()` переводит и многострочный текст разметки (внутри узла стоит перенос с
    отступом) и возвращает пробелы по краям узла — они разделяют соседние теги. Меняется и
    `<html lang>`. Уже открытая вкладка перерисовывается подписчиком `onLangChange`, отдельного
    обновления страницы не требуется. Новую надпись достаточно дописать парой в `PHRASES` — состав
    обоих словарей стережёт `tools/checks/i18n-check.mjs` (ключи RU/UK, пары фраз, подстановки);
  * тема: 6 схем (зелёная по умолчанию, синяя, индиго, бирюзовая, янтарная, графит). Перекраска
    сделана без пересборки Tailwind: на `<html>` меняется набор переменных `--brand*`, а правила в
    конце `css/theme.css` перекрывают классы Play CDN (`bg-[#15803d]`, `hover:bg-emerald-50/50`
    и т. п.). Если добавляете в разметку новый «зелёный» класс — допишите его в этот список, иначе
    он останется зелёным при другой схеме;
  * словарь применяется к готовому тексту, а не к его источнику: если в названии объекта или
    раздела сметы встретится слово из `PHRASES`, оно тоже переведётся («Объект №7» →
    «Об'єкт №7»). Это плата за то, что старые модули пишут подписи прямо в коде; там, где
    перевод в данных нежелателен, элемент помечают атрибутом `data-i18n-skip`;
  * i18n запоминает исходный русский текст каждого узла (WeakMap) и переводит только новое,
    поэтому повторные переключения RU ⇄ UK ничего не «затирают», а модули, которые перерисовывают
    список после смены языка, заново попадают под перевод.

## Ограничения и что стоит доделать

* **Tailwind подключён как Play CDN** (`cdn.tailwindcss.com/3.4.17`) — версия запинена, но SRI для него
  поставить нельзя: CDN не отдаёт `Access-Control-Allow-Origin`. Для продакшена правильнее собрать
  CSS заранее и отдавать локальный файл. Остальные CDN-скрипты (xlsx, supabase-js, frappe-gantt,
  html2canvas, jsPDF) уже подключены с `integrity` + `crossorigin`.
* **RLS в Supabase из фронтенда не проверяется.** Перед выдачей доступа убедитесь, что политики закрывают
  чтение/запись по ролям: фронтенд-проверки `can()` защитой не являются.
* **`database/schema.sql`** — реконструкция по коду (таблицы, колонки, внешние ключи), а не дамп боевой БД.
  Индексы, триггеры, RLS и настройки Storage здесь отсутствуют — сверяйтесь с реальной базой.
  Это **полная** схема вместе с изменениями v2.4.0, поэтому для уже развёрнутой базы применяйте не её,
  а пошаговые миграции: `database/migrate-v2.4.sql` (и предыдущие `migrate-v*.sql` по порядку);
  порядок применения и проверка — `database/README.md`.
  Миграция v2.4.0 добавляет 8 колонок в `orders` (`invoice_path`, `invoice_file_name`,
  `invoice_uploaded_at`, `invoice_total`, `payment_status`, `delivered_at`, `paid_at`,
  `paid_by_employee_id`), переводит старые заявки в `payment_status = 'paid'` и обновляет
  CHECK-ограничение `orders_status_check` (добавляет статус `delivered`, иначе заявка не
  закрывается). Отдельного бакета
  Storage не требуется: счета лежат в бакете чеков (`CONFIG.STORAGE.INVOICES_BUCKET`).
* Данные для офлайна не кэшируются: `sw.js` держит только оболочку приложения (html/css/js/иконки и
  библиотеки с CDN), а запросы к базе идут напрямую в сеть. При потере сети показывается
  предупреждающая полоса, сохранение в этот момент не сработает.
* **Инструкции обновлены под v2.4.0** (файлы 01–09 в `Документация/`, все PDF пересобраны):
  добавлен `Инструкция-09-Финансист` (рабочий стол, выдача по одобренным заявкам, счета на
  материалы, ведомость пополнений), у Директора описаны пополнение подотчёта финансиста и блок
  «🧾 Счета на материалы», у Снабженца переписан поток «🧾 Счёт от поставщика» → «🚚 Доставлено
  на объект», у всех ролей уточнены статусы заявок и добавлен раздел про «⚙ Настройки»
  (язык 🇷🇺/🇺🇦 и цветовая схема). Что именно менялось — таблица в `Документация/README.md`.
  Матрицу доступа в инструкциях нужно обновлять вместе с правками `js/permissions.js`.
  Раздел «9. Обновление базы данных» в инструкции Администратора дополнен разбором
  «наполовину применённой» миграции: SQL Editor останавливает скрипт на первой ошибке, поэтому
  команды миграции защищены, а в конце идёт самопроверка из 8 строк `ok`/`MISSING`
  (проверки — `tools/checks/migration-check.mjs` и `tools/checks/migration-run-check.mjs`).
* **`Презентация.html` / `Презентация.pdf` пока версии v2.1.0.** В ней нет роли «Финансист» и
  цепочки «счёт поставщика → доставка → оплата безналом», поэтому перед показом руководству её
  нужно переверстать под v2.4.0 — это переработка слайдов, а не автопересборка PDF.
* **Подтверждение email задаётся настройками Supabase, а не кодом.** Регистрация в приложении —
  только email и пароль, писем оно не отправляет, поэтому в проекте должна быть выключена опция
  *Confirm email*: иначе вход после регистрации падает с `Email not confirmed`, а письма на
  вымышленные адреса отскакивают и приводят к предупреждению Supabase о bounce-письмах. Что делать
  с уже созданными неподтверждёнными аккаунтами — в разделе «Регистрация и вход (email + пароль)».

## Проверка кода

Тестов и сборки нет. Минимальная проверка синтаксиса после правок — `node --check <файл>`:

```powershell
# все файлы приложения и проверок сразу (0 ошибок — всё разбирается)
foreach ($f in Get-ChildItem -Recurse -File -Include *.js,*.mjs js,tools) { node --check $f.FullName }
```

ES-модули (`js/main.js`, `js/modules/*.js` — в них есть `import`/`export`) проверяются так же:
Node 22+ определяет модуль по синтаксису сам, переименовывать файл в `.mjs` не нужно. На старых
Node (18–20) копия с расширением `.mjs` по-прежнему самый простой путь.

### Автопроверки (`tools/checks/`)

Часть прогонов поднимает локальный сервер, подменяет Supabase моком и открывает приложение в
настоящем Chrome — после правок логики можно убедиться, что интерфейс по-прежнему пишет в базу то,
что нужно, и какие роли что видят. Пять прогонов работают без браузера (только Node): SQL миграции,
словарь языков, НДС и своя доставка, живая схема базы:

```bash
node tools/checks/fin-workflow-check.mjs   # согласование заявок: прораб → директор → финансист (+ язык UK)
node tools/checks/invoice-check.mjs        # закупка: счёт → доставка → реестр → оплата (меню счетов, Excel), ведомость
$env:FLOW='order'; node tools/checks/fin-fix-check.mjs   # повторное создание заявки (кнопка не «залипает»)

node tools/checks/migration-check.mjs      # SQL миграций v2.4.0, v2.5.0 и v2.6.0: колонки, if not exists, защита от обрыва
node tools/checks/i18n-check.mjs           # словарь RU/UK: ключи, пары фраз, подстановки {name}, разметка (без браузера)
node tools/checks/vat-check.mjs            # НДС не начисляется дважды, своя доставка — расход объекта (без браузера)
node tools/checks/schema-live-check.mjs    # колонки v2.4.0/v2.5.0 в БОЕВОЙ базе (нужна сеть; запись не выполняется)
node tools/checks/migration-run-check.mjs  # те же миграции в настоящем Postgres: v2.4.0 и v2.6.0 (нужен @electric-sql/pglite)
```

Регрессии, которые стерегут именно эти проверки: карточка «Новой» заявки не должна показывать
«Оплачено», окно «🚚 Доставлено на объект» подписывает позиции по выбранному «кто платит», а в
позиции создаваемой заявки не пишется `payment_status`. Отдельно проверяется реакция на
**неприменённую миграцию**: мок отвечает как PostgREST на «наполовину обновлённой» базе (`42703` на
чтении, `PGRST204` на записи), и приложение обязано показать объяснение с именем колонки и файлом
`database/migrate-v2.4.sql`, а не пустые списки. И на **устаревшее CHECK-ограничение статусов**
(`23514`: «заявка не закрывается»): тост тоже должен вести к файлу миграции, а не показывать
английскую строку Postgres. Третья регрессия того же рода — **архив заявок на финансы**
(`23514` на `cash_requests_status_check`: «📥 В архив» и «✏️ На доработку»): подсказка обязана
называть `database/migrate-v2.6.sql`, а не файлы колонок v2.4.0/v2.5.0, иначе администратор
запускал не тот файл и видел ту же ошибку. Прогон в настоящем Postgres
(`migration-run-check.mjs`) проверяет, что миграции действительно обновляют оба ограничения —
`orders_status_check` (v2.4.0) и `cash_requests_status_check` (v2.6.0).

`vat-check.mjs` стережёт деньги счёта: НДС начисляется ровно один раз (галочки «+20 %» в приложении
нет — снабженец выбирает режим цены), своя доставка не попадает в счёт поставщика, а оплаченная из
подотчёта не считается второй раз строкой заявки. Он же проверяет, что подсказка при непройденной
миграции называет **именно тот файл**, который лечит ошибку: колонки НДС и своей доставки ведут к
`database/migrate-v2.5.sql`, остальные — к `database/migrate-v2.4.sql`.

`schema-live-check.mjs` проверяет **живую** базу, а не файлы: адрес и anon-ключ он берёт из
`js/config.js` (те же, что у приложения) и выгружает по одной колонке с `limit=1` через `/rest/v1/`.
Именно так и падает боевая база: код обновлён, а колонок миграции в Postgres ещё нет — «База данных
не обновлена: … нет колонки «invoice_price_mode»». Прогон печатает `ok` / `FAIL` по каждой колонке
v2.4.0 и v2.5.0, а в конце — какой файл применить и что проверить после (для «наполовину применённой»
миграции — что файл нужно запустить ещё раз целиком). Список колонок читается из самопроверок
`database/migrate-v2.4.sql` и `database/migrate-v2.5.sql`, поэтому разойтись с миграциями он не
может. В базу ничего не пишется (только `select`), так что запускать на боевой можно в любой момент;
другой проект проверяется переменными `SUPABASE_URL` / `SUPABASE_ANON_KEY`. В отчёт попадает только
хост — ключ не печатается. Ограничение `cash_requests_status_check` (миграция **v2.6.0**) этим
прогоном **не проверяется**: v2.6.0 колонок не добавляет, а список допустимых статусов через
`/rest/v1/` не виден. Его смотрят запросом в SQL Editor (`database/README.md` → «Как применить
`migrate-v2.6.sql`») или прогоном `migration-run-check.mjs`.

`i18n-check.mjs` следит за словарём языков: `t('ключ')` без ключа возвращает сам ключ, поэтому
непереведённая строка сразу видна в интерфейсе («order.paymentPending» вместо «⏳ Ожидает оплаты»).
Прогон сверяет ключи кода и разметки с разделами RU и UK, наборы ключей двух языков, подстановки
`{name}` и надписи рядом с `data-i18n` — на текущем коде он же нашёл устаревшую подсказку
`order.invoiceHint` (на украинском пропадала часть фразы). Отдельно проверяется фразовый словарь
`PHRASES`, по которому переводятся надписи старых модулей: прогон подключает тот же `js/i18n.js`,
что работает в браузере, и убеждается, что **каждая пара действительно переводит** свой русский
текст и что **ни одна пара не портит украинский** — русский шаблон не должен совпадать с
украинским текстом (так была найдена пара «всю → усю», которая переписывала уже переведённое
«щоб не змінити всю таблицю»), и что **у каждой надписи `index.html` есть перевод** — пара в
словаре или ключ `data-i18n`. Последняя проверка и стережёт исходную проблему: надпись в разметке
есть, а в словаре её нет — при переключении на украинский сотрудник видит русский текст.

Отчёты печатаются в консоль и сохраняются в `%TEMP%\rsk-fin\`. Папка `tools/` не публикуется на
хостинге (`.vercelignore`), подробности — в `tools/checks/README.md`.
