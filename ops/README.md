# Эксплуатация: выкладка, staging, резервные копии, мониторинг

Здесь то, что происходит **вокруг** приложения: как правка попадает к
сотрудникам, как проверить, что она доехала, где лежат резервные копии базы и
как узнать о сбое раньше, чем позвонят с объекта. Всё это лежит вне `index.html`
и `js/` — но ломается оно ровно так же, и часто незаметно.

Всё, что описано ниже, **проверяется прогоном** `tools/checks/ops-check.mjs`
(он входит в `npm run check` и в CI): файлы, триггеры задач GitHub, наличие
вызванных скриптов, совпадение журнала ошибок с миграцией базы и то, что каждый
секрет из задач упомянут в этом файле. Так инструкция не расходится с кодом.

## Что где лежит

| Файл | Зачем |
| --- | --- |
| `tools/ops/probe-live.mjs` | проба боевого адреса: страница, CSP, `sw.js`, манифест, стили, оболочка, CDN |
| `tools/ops/check-dump.mjs` | проверка дампа: не пустой, ключевые таблицы, распаковка, sha256 в манифест |
| `make-config.mjs` | подстановка базы staging при сборке (в корне — его зовёт сборка Vercel) |
| `.github/workflows/post-deploy.yml` | «боевой адрес отдаёт этот коммит» (после каждого push в `main`) |
| `.github/workflows/uptime.yml` | проба каждые 15 минут; при падении открывает issue |
| `.github/workflows/backup.yml` | ежедневный дамп базы + проверка восстановления на staging |
| `database/migrate-v2.9-ops-monitoring.sql` | таблица `app_errors` и команда `rsk_log_app_errors` (журнал ошибок) |
| `js/monitoring.js` | клиент журнала ошибок (перехват исключений и промисов) |

Выкладывает приложение **Vercel из этого же репозитория**: push в `main` —
боевая сборка, pull request — превью-адрес. Секретов для этого не нужно, и
дублировать выкладку из GitHub Actions не следует: два деплоя на один push
перезаписывали бы друг друга.

## Секреты

GitHub → **Settings → Secrets and variables → Actions → New repository secret**.

| Секрет | Кому нужен | Зачем | Где взять |
| --- | --- | --- | --- |
| `SITE_URL` | `post-deploy`, `uptime` | боевой адрес: без него обе задачи печатают предупреждение и ничего не проверяют | адрес приложения в Vercel (например `https://rsk-odessa.vercel.app`) |
| `SUPABASE_DB_URL` | `backup` | строка подключения к **боевой** базе для дампа | Supabase → Project Settings → Database → Connection string → **URI** (там же пароль) |
| `STAGING_DB_URL` | `backup` (вторая задача) | развернуть дамп на staging и убедиться, что копия рабочая | то же для staging-проекта Supabase |

**Если секрет не задан** — задача не падает молча: она печатает
предупреждение `::warning` («проба не выполнялась») или ошибку
(`SUPABASE_DB_URL`: «резервных копий нет»), и это видно в списке запусков.
Такой режим сделан нарочно, чтобы свежий клон репозитория не считался
сломанным, но и не выглядел защищённым.

Проверить, что секреты работают: **Actions → нужная задача → Run workflow**.

## Деплой

1. Правку делают в ветке → push → pull request. Vercel собирает **превью**
   по адресу ветки/PR: там проверяют работу.
2. После merge в `main` Vercel выкладывает боевую сборку, а задача
   **«Проверка после выкладки»** (`post-deploy.yml`) ждёт до 10 минут и
   проверяет, что боевой адрес отдаёт **именно этот коммит**:
   * `sw.js` — та же версия и та же ревизия (`SHELL_REVISION`), что в репозитории;
   * `css/tailwind.css` — тот же отпечаток сборки (`rsk-tailwind-build v… <хеш>`);
   * `js/config.js` — та же версия и тот же адрес базы;
   * политика CSP разрешает базу и все четыре хоста CDN (иначе service worker
     отдаёт 504 вместо библиотек);
   * вся офлайн-оболочка из `APP_SHELL` отвечает 200.
3. **Если задача упала** — приложение у сотрудников, скорее всего, старое.
   Что делать по каждой строке отчёта:

| Что не сошлось | Причина | Что делать |
| --- | --- | --- |
| отпечаток `css/tailwind.css` | сборку сделали, но не закоммитили (или наоборот) | `npm run build`, закоммитить `css/tailwind.css`, отправить снова |
| `SHELL_REVISION` на хостинге старый | Vercel ещё не закончил выкладку (задача ждёт 10 минут) или кэш CDN | проверить статус выкладки в Vercel; если выкладка зелёная — повторить задачу вручную |
| страница без `css/tailwind.css` | на хостинг уехал старый `index.html` | поднять `SHELL_REVISION` в `sw.js` (README → «Выпуск новой версии») |
| файл оболочки не отвечает 200 | файл забыли закоммитить или его выкинул `.vercelignore` | вернуть файл в репозиторий/убрать строку из `.vercelignore` |
| CSP без хостов CDN | правили `index.html`, но забыли `vercel.json` (или наоборот) | синхронизировать, обновить `sw.js` (иначе у сотрудников останется старая политика) |

Локально то же самое, без ожидания: `npm run probe -- https://<адрес>` (или
`node tools/ops/probe-live.mjs https://<адрес> --json`).

## Staging

Зачем: миграцию базы (`database/migrate-*.sql`) и новую правку надо обкатать на
копии, а не на боевых деньгах. Для этого — **второй проект Supabase** и **второй
проект Vercel**, оба рядом с боевыми и на бесплатных тарифах.

### 1. Второй проект Supabase

1. Supabase → New project (тот же регион, что боевой).
2. Применить схему по порядку: `database/schema.sql` → `migrate-v2.4.sql` →
   … → `migrate-v2.9-scale-indexes.sql` → `migrate-v2.9-ops-monitoring.sql`
   (см. `database/README.md`). Это «пустая, но правильная» база.
3. Auth → Providers → Email: **выключить «Confirm email»** (как на боевом —
   иначе вход после регистрации падает с `Email not confirmed`).
4. Завести тестового администратора и тестовый объект. **Боевые данные сюда
   переносить не нужно** — для проверок достаточно двух объектов и одного
   сотрудника.

### 2. Второй проект Vercel

1. Vercel → Add New → Project → тот же репозиторий.
2. **Production Branch: `staging`** — тогда боевая ветка `main` этот проект не
   трогает вообще.
3. Settings → **Build & Development Settings** (обязательно, иначе staging
   подключится к БОЕВОЙ базе):
   * Build Command: `node make-config.mjs`
   * Output Directory: `.`
   * Install Command: `echo зависимостей нет`
4. Settings → Environment Variables (Production и Preview):
   * `SUPABASE_URL` = адрес staging-базы (`https://<ref>.supabase.co` или свой
     Worker-прокси к ней — если завели, положите его адрес);
   * `SUPABASE_ANON_KEY` = publishable-ключ staging-проекта.
5. Settings → **Deployment Protection** → включить (Vercel Authentication):
   сотрудники не должны случайно попасть на стенд и поставить себе PWA с него.
6. Deploy. Проверить подмену: открыть стенд → DevTools → **Sources** →
   `js/config.js` — адрес базы должен быть staging, а не боевой. Если там
   боевой адрес — сборка не нашла переменные и упала (смотрите лог сборки).

### 3. Порядок обкатки

1. миграцию применяют на **staging** (Supabase → SQL Editor, файл целиком),
   смотрят на таблицу самопроверки (`ok` / `MISSING`);
2. на стенде проходят те же действия, что затронула правка (заявка, счёт,
   выдача денег — по смыслу изменения), смотрят журнал ошибок
   (раздел «Журнал ошибок» ниже) — там не должно появиться новых записей;
3. только после этого миграция применяется на **боевой** базе, а правка
   уезжает в `main`. **Перед боевой миграцией** запустить дамп вручную:
   Actions → «Резервная копия базы» → Run workflow.

## Резервные копии

Расписание: **ежедневно, 01:10 UTC** (`backup.yml`), плюс вручную перед любой
миграцией боевой базы.

Что получается: три файла (`roles.sql`, `schema.sql`, `data.sql`), сжатые в
`.gz`, плюс `backup-manifest.txt` (файл, размер, `sha256`, дата, коммит).
Хранятся **артефактом 90 дней** в GitHub: Actions → нужный запуск →
Artifacts → `db-backup`.

Проверка в самой задаче (`tools/ops/check-dump.mjs`): файлы не пустые, в схеме
есть ключевые таблицы приложения (`employees`, `projects`, `orders`,
`cash_operations`, `audit_log`, `app_errors`…), в данных есть `COPY`-блоки
сотрудников и объектов, архивы распаковываются. Если что-то из этого не так —
задача падает, и копия не считается сделанной.

### Восстановление

Автоматически (каждую ночь): вторая задача того же workflow скачивает дамп,
разворачивает его на **staging** и проверяет, что в `employees`, `projects` и
`orders` есть строки. Если строк нет — задача падает: «копия, которую не
разворачивали, копией не является».

Вручную (например, после ошибочного удаления данных):

```powershell
# 1. скачать артефакт db-backup, распаковать
gunzip dump/*.sql.gz
# 2. посмотреть, что внутри (манифест: дата, коммит, sha256)
Get-Content dump/backup-manifest.txt
# 3. развернуть на staging (или на новом проекте Supabase — так безопаснее)
psql "$env:STAGING_DB_URL" -v ON_ERROR_STOP=0 -f dump/schema.sql   # схема: часть объектов уже есть
psql "$env:STAGING_DB_URL" -v ON_ERROR_STOP=1 -f dump/data.sql     # данные: тут ошибка = копия неполная
```

Критерий «восстановление сработало»: приложение на стенде открывается, вход
тестовым администратором проходит, видны объекты и заявки, суммы в «Реестре» и
в кассе совпадают с ожидаемыми. Только после этого данные переносят на боевую
базу (или переключают приложение на восстановленный проект).

### Что нужно помнить

* Артефакт GitHub — **не off-site-копия**: 90 дней и внутри GitHub. Раз в месяц
  скачайте `db-backup` и положите в защищённую папку (диск в офисе, NAS).
* PITR (восстановление «на минуту назад») в бесплатном тарифе Supabase
  недоступен. Если данные станут дороже тарифа Pro — там ежедневные копии
  делаются самим Supabase, а наши задачи остаются как проверка восстановления.
* Дамп содержит **все** данные, включая деньги и фотографии чеков (ссылки).
  Поэтому артефакт доступен только тем, у кого есть доступ к репозиторию:
  не публикуйте его и не пересылайте в мессенджерах.

## Мониторинг

Три уровня — от «сайт не отвечает» до «у Ивана не сохраняется счёт».

### 1. Доступность (внешний сервис, 5 минут настройки)

Задача `uptime.yml` проверяет адрес каждые 15 минут и открывает issue при
сбое, но GitHub запускает расписание с задержками и может пропустить ночной
отказ. Поэтому заводится ещё и внешняя проверка (UptimeRobot, BetterStack,
Pingdom — на бесплатном тарифе):

* URL: `$SITE_URL` — тип **HTTP(s)**, ожидание **200** и ключевого слова
  `RSK Odessa` (так проверка не «пройдёт» по странице-заглушке хостера);
* URL: `$SITE_URL/sw.js` — ожидание 200 и слова `SHELL_REVISION` (это ловит
  случай, когда сайт открывается, а service worker не отдаётся);
* URL: `$SITE_URL/manifest.json` — ожидание 200 (манифест нужен для установки
  приложения).
* Оповещение: почта руководителя и админа; интервал проверки — 5 минут.

### 2. Своя проба (те же вопросы, что у внешней, но подробнее)

`uptime.yml` при падении прикладывает отчёт `probe-live` целиком (отдельный
для каждого шага: страница, CSP, `sw.js`, манифест, стили, оболочка, CDN) и
закрывает issue сам, когда адрес отвечает снова. Открытые задачи видно по
метке **`ops-monitoring`** — это и есть список «что сейчас сломано».

### 3. Журнал ошибок (что падает у сотрудников)

Ошибки браузера попадают в таблицу `app_errors`
(`database/migrate-v2.9-ops-monitoring.sql` + `js/monitoring.js`). Что важно
знать перед тем, как читать журнал:

* записываются **только** текст ошибки, стек, страница, версия и ревизия
  оболочки, сотрудник и роль. Сумм, файлов и паролей там нет;
* журнал **не растёт бесконечно**: записи старше 90 дней удаляются командой
  при следующей отправке, а при лавине (больше 200 записей за минуту) команда
  отвечает `rate_limited` и не пишет — иначе один сломанный экран забил бы
  таблицу за час;
* читают журнал **Администратор и Директор** (RLS). Остальным он не виден —
  это внутренняя диагностика, а не рабочие данные.

Готовые запросы (Supabase → SQL Editor):

```sql
-- 1. Что было за последние сутки: свежие сверху
select created_at, employee_id, role, kind, message, page, app_version, shell_revision
from public.app_errors
where created_at > now() - interval '1 day'
order by created_at desc
limit 100;

-- 2. Что повторяется чаще всего за неделю (с этого начинают разбор)
select kind, message, count(*) as times, min(created_at) as first_time, max(created_at) as last_time
from public.app_errors
where created_at > now() - interval '7 days'
group by kind, message
order by times desc
limit 30;

-- 3. У кого именно падает (кто видел больше всего ошибок за неделю)
select e.full_name, e.position, count(*) as errors
from public.app_errors as a
left join public.employees as e on e.id = a.employee_id
where a.created_at > now() - interval '7 days'
group by e.full_name, e.position
order by errors desc;

-- 4. Подробности одной ошибки: стек и подробности (context)
select created_at, employee_id, message, stack, page, context, user_agent
from public.app_errors
where message = 'ТЕКСТ ИЗ ЗАПРОСА 2'
order by created_at desc
limit 5;
```

Как разбирать результат:

| В журнале видно | Что это значит | Что делать |
| --- | --- | --- |
| `kind = save`, текст ошибки базы | сохранение не прошло (миграция, права, constraint) | сверить с `database/README.md` → таблица ответов базы; при необходимости применить нужную миграцию |
| `kind = error`, `message` про `xlsx`/`html2canvas`/`Gantt`/`supabase` | библиотека с CDN не загрузилась | проверить CSP (README → «Политика CSP») и что хост CDN в `connect-src`; если правили политику — обновить `sw.js` |
| `kind = rejection` | промис без обработчика (обычно забытый `await`) | найти по `stack` файл и строку, поправить; это настоящий баг, а не шум |
| много записей от одного сотрудника и мало от других | ошибка зависит от устройства/версии браузера | посмотреть `user_agent` и `shell_revision`: возможно, у него старая оболочка (см. «Выпуск новой версии») |
| пусто | ошибок нет либо не применена миграция журнала | проверить, что миграция применена (её самопроверка) и что у сотрудника свежая версия |

## Что осталось за рамками

* **Отчёт по ошибкам в интерфейсе.** Сейчас журнал читается SQL-запросом
  (выше). Отдельный экран «Диагностика» для админа — следующий шаг: данные для
  него уже есть (таблица, RLS, права), нужна только разметка и права в
  `js/permissions.js`.
* **Метрики использования** (кто и чем пользуется) не собираются вовсе:
  это отдельное решение о приватности, а не техническая недоделка.
* **Проверка миграций до боя** делается обкаткой на staging (см. выше). Если
  стенд не заведён, миграции применяются сразу на боевой — тогда обязателен
  ручной дамп перед применением.
