# Проверочные прогоны (автотесты приложения)

Эти файлы — не часть приложения. Это автопроверки. Большинство поднимает
локальный сервер, подменяет Supabase моком, открывает приложение в **настоящем
Chrome** и убеждается, что интерфейс делает именно то, что должен (какие строки
пишутся в базу, какие операции создаются, что видит каждая роль). Пять прогонов
работают вообще без браузера и без зависимостей: `migration-check.mjs`,
`i18n-check.mjs`, `vat-check.mjs`, `schema-live-check.mjs` (только Node; последнему
нужна ещё сеть — он спрашивает живую базу) и `migration-run-check.mjs` (нужен пакет
`@electric-sql/pglite`, без него прогон пропускается).

Приложение от этих файлов не зависит: папка `tools/` не публикуется на
хостинге (см. `.vercelignore`).

## Что нужно для запуска

* **Node.js 18+** (проверки используют `fetch` и `WebSocket`); для
  `node --check js/*.js` удобнее Node 22+ — он сам распознаёт ES-модули;
* **Google Chrome** (обычная установка в `C:\Program Files\Google\Chrome\...`) —
  только для браузерных прогонов.

Дополнительные пакеты ставить не нужно — только стандартная библиотека Node
(исключение — `migration-run-check.mjs`, см. выше). Установка пакетов
приложения (`npm install` в корне) нужна одному прогону: `frontend-check.mjs`
сверяет сборку Tailwind, а для точного сравнения ему нужен `node_modules/tailwindcss`
(без пакета он проверяет всё остальное и честно пишет «пропуск»).

## Как запускать

Из папки `tools/checks`:

```powershell
node invoice-check.mjs         # счёт → доставка → реестр → оплата (меню «ожидают / оплаченные», Excel)
node fin-workflow-check.mjs    # заявки финансов (прораб → директор → финансист), фильтры рабочего экрана, язык UK
node scale-check.mjs           # список заявок читается СТРАНИЦАМИ: offset/limit + count в запросе,
                               # вкладка и поиск уходят на сервер, «Показано 1-25 из 35»
$env:SCENARIO='A'; node fin-fix-check.mjs              # заявка финансов, сценарий A (успех)
$env:FLOW='order'; node fin-fix-check.mjs              # то же для заявки на материалы

node migration-check.mjs       # статические проверки SQL миграций v2.4.0 … v2.9.0 (браузер не нужен)
node migration-run-check.mjs   # миграции v2.4.0 и v2.6.0 в настоящем Postgres (нужен пакет @electric-sql/pglite)
node i18n-check.mjs            # словарь языков: ключи RU/UK, пары фраз, подстановки, разметка (браузер не нужен)
node vat-check.mjs             # НДС не начисляется дважды и своя доставка — расход объекта (браузер не нужен)
node frontend-check.mjs        # фронтенд для прода: сборка Tailwind, data-action, CSP, линтер, CI (браузер не нужен)
node schema-live-check.mjs     # схема БОЕВОЙ базы: колонки миграций v2.4.0/v2.5.0, закрыты ли финансы
                               # от anon (v2.7.0) и создан ли журнал audit_log (v2.8.0) — нужна сеть
```

Из корня репозитория то же самое собирается в короткие команды (и так же
запускается в CI, см. `.github/workflows/ci.yml`):

```bash
npm run check           # migration-check → i18n-check → vat-check → frontend-check
npm run check:browser   # invoice, fin-workflow, scale (нужен Chrome)
npm run check:db        # migration-run-check + schema-live-check (pglite и живая база)
npm run build           # сборка css/tailwind.css (пересобрать после правки классов)
npm run lint            # eslint: встроенные обработчики и мёртвый код
```

`migration-check.mjs` — обычная проверка без браузера и без зависимостей: она
сверяет `database/migrate-v2.4.sql` и `database/schema.sql`, следит, чтобы
колонки добавлялись только с `if not exists` и в защищённых блоках, ищет в SQL
типографские кавычки и невидимые пробелы (из-за них команда молча ломается при
копировании из документа) и проверяет, что миграция обновляет CHECK-ограничение
`orders_status_check` под статус `delivered`. Отдельным блоком стережётся
миграция **v2.5.0** (`database/migrate-v2.5.sql` — НДС и своя доставка): её
колонки, защищённые блоки, самопроверка `ok / MISSING`, `notify pgrst` и
заполнение вида доставки у старых строк. Типографские кавычки ищутся и внутри
строковых литералов — поэтому в боевом SQL подписи пишутся обычными кавычками
(`у строк "Доставка компании"`), а «ёлочки» остаются только в комментариях: файл
копируют в SQL Editor руками. Тем же набором проверок стережётся
и служебный файл `database/fix-orders-status-check.sql`, а отдельным блоком — **v2.6.0**
(`database/migrate-v2.6.sql`: архив заявок на финансы, правка CHECK-ограничения
`cash_requests_status_check`, ни одного `add column`), включая сверку шести статусов с
`js/modules/cash-requests.js`.

Дальше идут два блока, которые стерегут **защиту финансов**. Они появились потому, что эти
миграции колонок не добавляют, а значит по колонкам их «не увидеть»: `schema-live-check.mjs`
проверяет колонки, а не политики. Поэтому живой прогон ловит из этих миграций ровно то, что
видно анонимным ключом (закрыты ли финансы, есть ли журнал `audit_log`), а всё остальное —
`migration-check.mjs` по тексту файлов:

* **v2.7.0** (`database/migrate-v2.7-rls-finance.sql`) — RLS на `cash_requests` и
  `cash_operations`. Проверяется, что обе функции-контекста (`rsk_current_employee_id`,
  `rsk_current_employee_role`) объявлены `security definer` с фиксированным
  `search_path = pg_catalog, public` (иначе подстановка чужой схемы меняет смысл политики) и
  выданы только роли `authenticated`, что у `anon` отобраны права на обе таблицы, что RLS
  включён **и форсирован** (без `force row level security` владелец таблицы обходил бы
  политики), что каждая из 15 политик (6 у заявок, 9 у операций) сначала снимается через
  `drop policy if exists` (файл запускают повторно), и что в самопроверке есть
  `relforcerowsecurity`, `pg_policies` и права `anon`. Там же сверяется **матрица прав
  приложения** (`js/permissions.js` → `ROLE_PERMISSIONS`) со списками ролей в политиках: право
  `cash_issue` — с политикой кассы (`rsk_cash_operations_insert_cashier`), права
  `cash_expense_self` и `cash_return_self` — с политикой «за себя»
  (`rsk_cash_operations_insert_self`, у Финансиста там только `return` с `source is null`), а
  `process_order` — с той же политикой расхода: закрытие заявки с оплатой из подотчёта
  (`js/modules/orders.js` → `closeOrder`) пишет `cash_operations` напрямую, `source = 'order'`.
  Расхождение этих двух списков видно только в бою — кнопка есть, а база запись отклоняет («new
  row violates row-level security policy»), — поэтому список ролей нельзя расширить в
  интерфейсе, не поправив политику;
* **v2.8.0** (`database/migrate-v2.8-finance-rpc-audit.sql`) — транзакционные команды.
  Список команд прогон берёт **из кода** (`js/database.js` → `RPC`), а не из SQL: именно код
  зовёт команды по имени, и опечатка даёт `PGRST202` («функция не найдена») уже в бою. Для
  каждой команды проверяется объявление `create or replace function`, `revoke all … from
  public` и `grant execute … to authenticated` (а также что `anon` execute не выдан), закрытый
  прямой `insert` в `orders`/`cash_requests`, снятие всех пяти временных политик v2.7.0 (и что
  заново они не создаются), журнал `audit_log` (клиенту — только `select`, RLS enabled +
  forced), уникальный ключ идемпотентности `audit_log_command_once`, отметка
  `perform rsk_write_audit` у каждой команды, единственная своя доставка на заявку
  (`cash_operations_one_own_delivery_per_order` плюс отказ на исторических дублях) и подсказка
  «Сначала примените database/migrate-v2.7-rls-finance.sql», если предыдущей миграции нет.
  Те же имена команд прогон ищет в списке самопроверки файла. Отдельно сверяются **исходники
  приложения**: в `js/` и `js/modules/` не должно остаться `db.insert('orders'…)` или
  `db.insert('cash_requests'…)` (такую запись всё равно отклонит база после `revoke insert`),
  а вызовов `db.rpc(...)` с ключом `db.newCommandKey()` должно быть не меньше числа команд;
* **v2.9.0** (`database/migrate-v2.9-scale-indexes.sql`) — индексы под страницы. Файл сам по себе
  скромный (ни колонок, ни политик), поэтому его стерегут «от противного»: проверяется, что кроме
  `create index if not exists`, `analyze`, `begin`/`commit` и самопроверки в файле **ничего нет** —
  ни `drop`, ни `alter`, ни `insert`/`update`/`delete`, ни `revoke`/`grant`, ни `create table`/
  `create policy` (иначе «масштабирование» стало бы миграцией, которую страшно применять на живой
  базе). Дальше — что все 28 индексов создаются идемпотентно, что список индексов из определений
  совпадает со списком в самопроверке (индекс, забытый в ней, выглядит как `MISSING` у
  администратора) и что **у каждой колонки, по которой списки фильтруют и сортируют на сервере,
  есть индекс**: список этих колонок (`orders.status`, `orders.created_at`,
  `orders.created_by_employee_id`, `cash_operations.operation_date`, `tasks.deadline`,
  `employees.user_id` …) ведётся прямо в прогоне. Отдельные проверки — про код: список заявок
  обязан читаться `db.selectPage('orders', …)` (а не `db.select('orders'…)` всей таблицей),
  вкладки и права прораба и поиск обязаны уходить условиями запроса (а не фильтром в браузере),
  панель списка (`js/pagination.js`) должна существовать, быть подключённой в кэш оболочки
  (`sw.js`) и иметь место в разметке (`#orders-toolbar`), условия поиска собираться **без своих
  скобок** (иначе в запрос уйдёт `or=((…))` и PostgREST ответит `PGRST100`), а версия приложения
  совпадать в `js/config.js` и `sw.js`.

`migration-run-check.mjs` делает то же самое «по-настоящему»: поднимает Postgres
в памяти (PGlite) в состоянии боевой базы «миграция применилась наполовину»
(включая старое CHECK-ограничение `orders_status_check` без статуса
`delivered`), выполняет файл миграции и проверяет, что колонок стало 8,
`payment_status` получил `default 'paid'`, самопроверка печатает 8 строк `ok`,
**до миграции заявку нельзя перевести в `delivered` (та самая боевая ошибка),
а после — можно**, проверка ограничения печатает `ok`, повторный запуск
безопасен и при сбое `alter table` скрипт всё равно доходит до конца, сообщая
`MISSING`. Отдельно так же проверяется служебный файл
`database/fix-orders-status-check.sql`. Второй сценарий — миграция **v2.6.0**
(`database/migrate-v2.6.sql`): на `cash_requests` ставится боевое ограничение без `archived` и
`revision`, и прогон убеждается, что «📥 В архив» и «✏️ На доработку» до миграции падают именно с
боевой ошибкой `cash_requests_status_check`, что самопроверка файла до правки честно печатает
`MISSING`, а после — шесть строк `ok`, что ограничение разрешает все шесть статусов кода,
повторный запуск безопасен и колонок файл не добавляет. Пакет ставится только для этого прогона
(`npm install @electric-sql/pglite`); нет пакета — прогон пропускается.

`i18n-check.mjs` — тоже без браузера и без зависимостей: он сверяет словарь
языков `js/i18n.js` с тем, что просит интерфейс. Проверяет, что каждый ключ из
`t('...')` в `js/modules/*.js` и из `data-i18n="..."` в `index.html` есть и в
русском, и в украинском словаре (`t()` без ключа возвращает сам ключ — сотрудник
увидел бы «order.paymentPending» вместо «⏳ Ожидает оплаты»), что наборы ключей
RU и UK совпадают, что подстановки `{number}` из вызовов `t('ключ', { ... })`
есть в текстах обоих языков, что надпись рядом с `data-i18n` в разметке не
разошлась со словарём (иначе при переключении RU → UK → RU текст «прыгает»),
и что в словаре нет ключей-дублей. Неиспользуемые ключи печатаются как
примечание `note` — это не ошибка. Прогон уже нашёл расхождение: подсказка
`order.invoiceHint` в разметке дописалась словами «а заявка перейдёт в «Ожидает
оплаты»», а в словаре осталась старая версия — то есть на украинском эта часть
фразы пропадала.

Второй словарь — **фразовый** (`PHRASES`: пары «русский текст → украинский»,
по которым переводятся надписи старых модулей прямо в готовом DOM). Его прогон
проверяет «по-живому»: подключает тот же `js/i18n.js`, что работает в браузере,
и вызывает `translateText()`:

* каждая пара действительно переводит свой русский текст — иначе пара молча не
  срабатывает (опечатка, другой регистр или конфликт с более длинной фразой);
* ни одна пара не портит УЖЕ украинский текст: русский шаблон не совпадает с
  украинским. Так была поймана пара `всю → усю`: она применялась к готовому
  переводу и превращала «щоб не змінити всю таблицю» в «...усю таблицю». Поэтому
  в словарь нельзя добавлять пары, чей русский текст встречается и в украинском
  (сейчас прогон проверяет около 1250 украинских текстов — и ключи `DICT`, и все пары);
* нет пар с одинаковым русским текстом: такая надпись переводилась бы то одним,
  то другим способом в зависимости от порядка строк в словаре;
* у каждой надписи `index.html` (текст узла или `placeholder` / `title` /
  `aria-label`) есть перевод — пара в словаре или ключ `data-i18n`. Это и есть
  сторож исходной проблемы: надпись в разметке есть, а в словаре её нет, и при
  переключении на украинский сотрудник видит русский текст. Надписи, которые в
  RU и UK пишутся одинаково («Дата», «Оплата», «Ставка ПДВ, %»), перечислены
  в списке `SAME_IN_BOTH` файла прогона: если появится новое такое слово,
  прогон скажет, что надпись осталась русской, — слово нужно дописать в список.

`vat-check.mjs` — тоже без браузера и без зависимостей, но в отличие от остальных
он **загружает настоящий код приложения** (`js/utils.js` и `js/config.js` — их
функции вызываются напрямую) и читает текст `index.html`, `js/modules/orders.js`,
`js/i18n.js` и `database/migrate-v2.5.sql`, сверяя их между собой. Зачем:
в v2.5.0 у счёта появились режим цены (`orders.invoice_price_mode`), ставка НДС и
своя доставка, и две ошибки в этой логике тихие — сумма выглядит правдоподобно,
но неверна. Прогон стережёт обе:

1. **налог не начисляется дважды.** Если цены уже с НДС, `utils.calcVat()`
   обязан ВЫДЕЛИТЬ налог из суммы (`base + vat === total`, итог не растёт);
   если без НДС — добавить его сверху ровно один раз. Отдельно проверяется, что
   повторное сохранение счёта ничего не меняет (налог не «накапливается»),
   ставка 0 % не добавляет ничего, `vatFromTotal()` именно выделяет налог из
   готовой суммы, `normalizeVatRate()` не пропускает мусор и минус, а режим по
   умолчанию — безопасный («цены уже с ПДВ»). Суммы проверяются до копейки на
   наборе из нескольких сумм и ставок (0 / 7 / 20 / 20,5 %), потому что ошибка
   вылезает именно на округлении;
2. **своя доставка — внутренний расход, а не деньги поставщика.** Строка
   «Доставка компании» не входит в счёт поставщика (и её НДС тоже) и показывается
   как «🏢 Вне счёта». Если её оплатили из подотчёта, `orders.js` создаёт
   `cash_operation` с `source = 'own_delivery'`, и тогда строка заявки из денег
   исключается (`utils.isOwnDeliveryCovered()`) — иначе сумма попала бы в план-факт,
   реестр и «Доп. расходы» дважды: строкой заявки и расходом подотчёта. Прогон
   проверяет и обратное: доставка поставщика из денег НЕ исключается (она уже
   внутри счёта), у неоплаченной своей доставки остаётся «🏢 Вне счёта», а обычная
   позиция заявки под эту проверку не попадает. Отдельно сверяется, что общая
   проверка живёт в одном месте (`js/utils.js`), ею пользуются `cash.js`,
   `dashboard.js` и `registry.js`, а вид доставки читается из колонки
   `delivery_kind` (со старым запасным вариантом «по имени строки» для строк,
   созданных до v2.5.0);
3. **разметка окна счёта совпадает с `CONFIG`:** два режима цены и оба вида
   доставки в `index.html` — ровно те значения, что в `CONFIG.VAT.MODE` и
   `CONFIG.DELIVERY_ITEM.TYPE`; у поля ставки границы 0…100 и значение по
   умолчанию из конфига; варианты «чем списываем свою доставку» совпадают с
   `CONFIG.DELIVERY_ITEM.CHARGE`; и главное — **в разметке нет галочки «начислить
   НДС»** (снабженец выбирает режим цены, а не второе начисление);
4. **налог считается в одном месте:** в коде нет «ручного» `×1,2`, суммы позиций
   сохраняются уже с НДС (`price_with_vat`), расшифровка «в т.ч. ПДВ» — это
   выделение налога, режим и ставка сохраняются вместе со счётом;
5. **база и словарь:** все 12 колонок v2.5.0 (`orders`, `order_items`,
   `cash_operations`) перечислены в самопроверке миграции, описаны в
   `schema.sql`, значения в базе совпадают с `CONFIG`, старым строкам доставки
   проставляется `delivery_kind`, а подписи НДС и своей доставки есть и в
   русском, и в украинском словаре;
6. **подсказка при непройденной миграции называет НУЖНЫЙ файл.** Прогон
   вызывает настоящий `js/database.js` → `explainError()`: колонки НДС и своей
   доставки (10 имён из 12 колонок миграции) обязаны вести к
   `database/migrate-v2.5.sql`, колонки v2.4.0 (`payment_status`, `delivered_at`,
   `invoice_total`…) — к `database/migrate-v2.4.sql`, а незнакомая колонка — к
   базовой v2.4.0 (выдумывать несуществующий файл нельзя: он проверяется и на
   диске). Список колонок в коде сверяется со списком миграции, чтобы они не
   разошлись. Раньше на любую отсутствующую колонку приложение отвечало
   «примените migrate-v2.4.sql», и администратор запускал не тот файл, получая
   ту же ошибку второй раз.

   Отдельно проверяется подсказка в **консоли** (её администратор читает, когда
   сам ищет причину): она обязана называть версию нужной миграции — «база
   не обновлена под v2.4.0» для `payment_status`, а не версию приложения
   («под v2.5.0»), иначе подсказка снова уводит не к тому файлу.

Проверено, что прогон действительно ловит поломку: если в `utils.js` заменить
выделение налога на начисление сверху, падают сразу 4 проверки — «цены уже с
ПДВ», «пересохранение», «base + vat === total» и «vatFromTotal». Если в
`js/database.js` заставить `migrationForColumn()` всегда возвращать v2.4.0,
падает проверка блока 5б «отсутствие колонки v2.5.0 ведёт к migrate-v2.5.sql».
Если вернуть в консольную подсказку версию приложения
(`CONFIG.APP.VERSION` вместо `migration.version`), падает проверка
«консоль называет версию нужной миграции (v2.4.0), а не версию приложения».

`schema-live-check.mjs` — единственный прогон, который смотрит не в файлы, а в **живую базу**.
Повод: приложение и база обновляются отдельно, и сотрудник при сохранении счёта читает «База
данных не обновлена: в таблице «orders» нет колонки «invoice_price_mode». Примените
`database/migrate-v2.5.sql`». Это не баг интерфейса, а неприменённая миграция — но увидеть это
можно только на боевой базе. Прогон берёт адрес и anon-ключ из `js/config.js` (те же, что у
приложения) и спрашивает базу **тем же способом**, что и приложение: выгружает одну колонку с
`limit=1` через `/rest/v1/`. Колонка есть — `ok`, PostgREST ответил `42703` или `PGRST204` —
`FAIL` с именем файла миграции. В конце — блок «ЧТО ДЕЛАТЬ»: какие колонки не на месте, каким
файлом их добавить и что проверить после (для «наполовину применённой» миграции — отдельная
строка «миграция применена НАПОЛОВИНУ, запустите файл ещё раз целиком»).

Список колонок не выдуман: он читается из самопроверок `database/migrate-v2.4.sql` (8 колонок)
и `database/migrate-v2.5.sql` (12 колонок), поэтому разойтись с миграциями прогон не может —
если в SQL добавили колонку, он напомнит про неё. Запись в базу не выполняется ни при каком
исходе (только `select ... limit=1`), поэтому запускать на боевой базе можно в любой момент.
Другую базу можно проверить без правки файла: `SUPABASE_URL` и `SUPABASE_ANON_KEY` в переменных
окружения. Ключ в отчёт не попадает — печатается только хост.

Ключ в приложении **анонимный**, а с v2.7.0 финансы закрыты именно от него: `cash_operations`
и `cash_requests` отвечают `401` / `42501` («permission denied»). Поэтому две колонки v2.5.0 в
`cash_operations` (`vat_rate`, `vat_amount`) прогон помечает строкой `note … таблица закрыта для
anon (RLS v2.7.0), колонку проверяет SQL Editor` и **не считает их пропажей** — иначе после
правильной миграции прогон краснел бы на ровном месте. В итоге этих строк написано, сколько
колонок осталось непроверенными, и куда за ними смотреть (SQL Editor, раздел «Как применить
`migrate-v2.7-rls-finance.sql`» в `database/README.md`).

Тот же ответ базы прогон использует как **живую проверку защиты и команд**: отдельный блок
«Защита финансов и журнал команд (v2.7.0 / v2.8.0)» требует, чтобы `cash_requests` и
`cash_operations` были закрыты для anon (до v2.7.0 они отвечали `200`, то есть любой человек с
ключом из исходников читал чужие заявки и кассу), а таблица `audit_log` из v2.8.0
**существовала** — до её применения PostgREST отвечает `404` / `PGRST205` «Could not find the
table». Так две из трёх последних миграций видны прямо из боевой базы, без SQL Editor.

Миграции **v2.6.0** этим прогоном не проверяются, и это не упущение: она колонок не добавляет, а
список допустимых статусов (`cash_requests_status_check`) через `/rest/v1/` не виден. Его
состояние смотрят запросом в SQL Editor (раздел «Как применить …» в `database/README.md`) или
прогонами `migration-run-check.mjs` (SQL выполняется в настоящем Postgres) и
`migration-check.mjs` (файлы миграций читаются по тексту). У v2.7.0 и v2.8.0 так же не видны
политики RLS, права на функции и совпадение объявлений с `js/database.js` → `RPC` — это дело
`migration-check.mjs`. **Индексы v2.9.0** живой прогон не видит вообще (через `/rest/v1/` они не
видны, а в `database/schema.sql` их нет): их список и связку «фильтр в коде ↔ индекс» стережёт
`migration-check.mjs`, а живые индексы можно посмотреть только запросом в SQL Editor —
`select indexname from pg_indexes where schemaname = 'public' order by indexname;`

Способа «увидеть v2.8.0 через `OpenAPI`» не существует, и пробовать его не нужно: описание схемы
PostgREST отдаёт только по **секретному** ключу (анонимному в ответ приходит
`401 {"message":"Secret API key required"}`), а сами четыре команды v2.8.0 вызываются лишь ролью
`authenticated` (`revoke all … from anon` + `grant execute … to authenticated`), поэтому в
описании для анонимного вызова их не было бы и при открытом эндпоинте. Анонимно от v2.8.0 видно
ровно одно — таблица `audit_log` появилась (это и проверяет `schema-live-check.mjs`); остальное
стережёт `migration-check.mjs` по тексту файла.

Браузерные прогоны подменяют Supabase моком, поэтому мок знает и серверные команды v2.8.0: запрос
на `/rest/v1/rpc/<команда>` отвечает тем, что ответила бы база, — номером заявки «Ф-N/YY» (или
«№ N/YY»), позициями, обеими операциями выдачи, а `save_own_delivery_expense` — действием над
расходом (`created` / `updated` / `deleted` / `unchanged`) с суммой и НДС. Ошибки мок отдаёт теми
же кодами, что Postgres. Это ловит три поломки:

* команду зовут с нужным телом и **ключом идемпотентности** (`db.newCommandKey()`): без ключа база
  отвечает `22023`, и мок отвечает так же;
* **нет прямой записи в `orders` и `cash_requests`** — каждый `POST` в эти таблицы мок запоминает,
  печатает в конце прогона и валит строку «заявки создаются серверной командой, а не прямой записью
  в таблицу», показывая тело запроса. После v2.8.0 такой запрос отклоняет и база (`revoke insert`),
  поэтому это сторож регрессии «заявка создаётся, но часть кода вернулась к прямой записи»;
* отказ команды сотрудник видит человеческим текстом: `22023` (нет ключа или сумма не та), `42501`
  (нет роли или не применены политики RLS, сценарий `B`), `P0001`/`P0002` (заявка не в том статусе
  или не найдена), `PGRST202` (команды нет в базе). Текст подсказки собирает
  `js/database.js` → `parseRpcFailure`, и в нём названы файлы `migrate-v2.7-rls-finance.sql` и
  `migrate-v2.8-finance-rpc-audit.sql`: по этой строке видно, что сотруднику предложено ровно то,
  что нужно применить.

Chrome для прогонов запускается в отдельном профиле (`%TEMP%\rsk-fin\chrome-profile`,
`chrome-profile-workflow`, `chrome-profile-invoice`) и удаляется перед прогоном, чтобы не мешать
рабочему браузеру. На Windows папку прошлого прогона может не отпустить система (`EPERM`: процессы
Chrome живут ещё несколько секунд после `kill`), поэтому при отказе удаления берётся папка с
добавленным номером процесса — прогон из-за профиля не падает.

Пути можно переопределить переменными окружения:

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `APP_ROOT` | корень репозитория (на две папки выше) | если приложение лежит в другой папке |
| `CHROME_PATH` | `C:/Program Files/Google/Chrome/Application/chrome.exe` | если Chrome установлен иначе |
| `SCENARIO` | `A` | сценарий ответа базы в `fin-fix-check.mjs`: `A` — команда выполнена, `B` — нет прав (403 + `42501`), `C` — ответ 200 без тела (итог транзакции неизвестен) |
| `FLOW` | `finance` | тип заявки в `fin-fix-check.mjs`: `finance` — заявка на работы (деньги), `order` — заявка на материалы; он же попадает в имя отчёта (`fin-fix-finance.txt`) |
| `SUPABASE_URL` | `CONFIG.SUPABASE_URL` из `js/config.js` | `schema-live-check.mjs`: проверить другую базу (например, тестовый проект) |
| `SUPABASE_ANON_KEY` | `CONFIG.SUPABASE_ANON_KEY` из `js/config.js` | то же: anon-ключ к этой базе |

## Куда смотреть результат

Каждый прогон печатает отчёт в консоль (`  ok  ` по каждой проверке) и
дополнительно кладёт его в текстовый файл в `%TEMP%\rsk-fin\`:

* `invoice-check.txt`, `fin-workflow.txt`, `fin-fix-finance.txt`, `fin-fix-order.txt`,
  `migration-check.txt`, `migration-run-check.txt`, `i18n-check.txt`,
  `vat-check.txt`, `frontend-check.txt`, `schema-live-check.txt`;
* `fin-workflow-uk.txt` — текст рабочего экрана после переключения языка на
  украинский (последняя проверка `fin-workflow-check.mjs`): по нему видно, что
  именно осталось русским, если прогон пожалуется на непереведённую надпись.

В конце отчёта — строка «ВСЁ ВЕРНО…» или список непрошедших проверок, а также
фактическое состояние мок-базы (заявки, операции, балансы) и ошибки консоли
браузера. Если в консоли появились исключения, прогон считается неуспешным —
это ловит сломанные обработчики, которые не видны по тексту на экране.
Все прогоны возвращают **код 1**, если есть непройденные проверки (и 0, если всё
хорошо) — можно ставить в автоматику, не читая отчёт глазами. Исключение —
`migration-run-check.mjs` без пакета `@electric-sql/pglite`: он печатает
«прогон пропущен» и возвращает 0.

## Что именно проверяет `frontend-check.mjs`

Прогон появился вместе с этапом «Фронтенд для прода»: Tailwind перестал
подключаться как Play CDN (`cdn.tailwindcss.com`) и собирается заранее
(`npm run build` → `css/tailwind.css`), а вместо встроенных обработчиков
(`onclick="..."`) разметка называет действие (`data-action`, см. `js/actions.js`),
иначе Content-Security-Policy пришлось бы разрешить `'unsafe-inline'` — то есть
вставить скрипт в страницу мог бы любой подставленный текст. Оба изменения
ломаются МОЛЧА, поэтому у них есть прогон:

1. **Tailwind собран локально.** В `index.html` не должно остаться тега с
   `cdn.tailwindcss.com`; должно быть подключение `./css/tailwind.css` и в том же
   порядке, что раньше (после `css/style.css`, до `css/theme.css` — последняя
   перекрашивает «фирменные» утилиты под выбранную тему). `src/tailwind.css`
   (исходник с `@tailwind base/components/utilities`) на месте, а `css/tailwind.css`
   — действительно собранный файл. Оба новых файла (`css/tailwind.css`,
   `js/actions.js`) есть в офлайн-оболочке `sw.js` → `APP_SHELL`.
2. **Отпечаток сборки** (`/* rsk-tailwind-build v2.9.0 <отпечаток> */` в конце
   файла) совпадает с текущим содержимым `index.html` и всех модулей `js/**`, а версия —
   с `js/config.js` и `sw.js`.
3. **Точная пересборка**: если установлен `node_modules/tailwindcss`, прогон
   запускает сборку заново и сравнивает результат с закоммиченным файлом байт в байт.
   Это ловит ситуацию «класс добавили, `npm run build` забыли»: Play CDN раньше
   дорисовывал такой класс на лету, статическая сборка — нет, и кнопка просто теряла цвет.
4. **Все классы на месте**: из разметки и шаблонов модулей собираются имена классов
   (388 штук) и проверяются в готовом CSS. Свои классы (`app-loading`,
   `cashreq-item-name`) ищутся в `css/style.css` и `css/theme.css`, классы-маркеры
   (по ним модули находят поля формы через `querySelector`) — в коде. Отдельно
   проверяются классы, собираемые из поля (`badge` групп задач): такое имя класса
   Tailwind не видит в разметке.
5. **Встроенных обработчиков нет** ни в `index.html`, ни в `js/**` (двадцать
   событий, включая `onerror` и `onkeydown`).
6. **Каждое `data-action` нажимается**: имя действия есть среди `window.*`
   (диспетчер ищет его там, см. `js/actions.js`). Проверено 116 действий —
   опечатка в имени иначе просто не нажималась бы. Здесь же проверяется, что у
   картинки с `data-fallback-show` есть запасной блок с таким `id`.
7. **CSP**: политика в `index.html` (`<meta http-equiv>`) и заголовок в
   `vercel.json` совпадают директива за директивой (браузер применяет обе), в
   `script-src` нет `'unsafe-inline'`/`'unsafe-eval'`, `default-src 'self'`,
   каждый внешний файл разметки разрешён нужной директивой, `'unsafe-inline'`
   остался только в `style-src` (ширины полос прогресса задаются атрибутом
   `style`), а адрес базы из `js/config.js` разрешён в `connect-src`.
8. **Инструменты на месте**: линтер (`eslint.config.mjs` с запретом встроенных
   обработчиков), скрипты `build`/`lint` в `package.json`, замок зависимостей
   (`package-lock.json` нужен для `npm ci`), сборка прогонов в CI
   (`.github/workflows/ci.yml`) и `.vercelignore`, который не выкидывает с
   хостинга `index.html`, `css/`, `js/` и не отправляет туда `node_modules/`.

Отчёт: `%TEMP%\rsk-fin\frontend-check.txt`. Код возврата 1 при замечаниях.

## Что именно проверяет `scale-check.mjs`

Этот прогон появился вместе с этапом «Масштабирование» (v2.9.0), когда список заявок перестал
грузить таблицу целиком. Он поднимает приложение с **60 заявками** в моке (35 «активных»,
страница — 25) и мок отвечает как PostgREST: понимает `status=in.(…)`, `or=(…ilike…)`, режет
ответ по `offset`/`limit` и при `Prefer: count=exact` присылает общее число строк в
`Content-Range`. Что проверяется по шагам:

1. **Список читается страницей.** Раздел «Снабжение» показывает ровно 25 карточек, а в запрос
   уходят `offset=0&limit=25`, `Prefer: count=exact` и `status=in.(new,in_progress)` — то есть
   вкладка статуса фильтрует **база**, а не браузер;
2. **«Выгрузи всё» больше нет.** Отдельная проверка просматривает все запросы к `/orders` за
   прогон: у каждого обязано быть ограничение (`limit` ≤ 100). Именно этот пункт ловит возврат к
   старой схеме «загрузить таблицу и отфильтровать в JS»;
3. **Надпись считает база**: «Показано 1-25 из 35» — 35 берётся из `count`, а не из выгруженного;
   на первой странице «‹ Назад» выключена, на последней — «Вперёд ›»;
4. **Страницы листаются смещением.** «Вперёд ›» уходит с `offset=25&limit=25`, показывает 10
   оставшихся заявок (26-35) и **другие** номера, а не первые 25 повторно;
5. **Поиск — условие запроса.** Ввод в поле поиска отправляет
   `or=(request_number.ilike.%трубы%,supplier.ilike.%трубы%)`, возвращает только подходящие
   заявки (3 из 60) и снова с первой страницы. Заодно проверяется, что условие собрано **без
   своих скобок**: со своими в запрос уйдёт `or=((…))`, PostgREST ответит `PGRST100`, и поиск
   молча ничего не найдёт (мок отвечает так же, и прогон это ловит);
6. **Смена вкладки — новый запрос**: «🟢 Закрытые» уходит условием `status=eq.closed` и
   показывает все 10 закрытых заявок.

Паузы между действиями прогон делает **внутри страницы**: поиск отвечает по дебаунсу (350 мс), а
страничные запросы асинхронны, поэтому «нажали и сразу прочитали DOM» показывало бы прошлый
список (в первых прогонах так и было).

## Что именно проверяет `invoice-check.mjs`

Цепочка закупки материалов, ради которой прогон и написан:

1. **Снабженец** создаёт заявку, открывает «🧾 Счёт от поставщика», заполняет
   поставщика и цены, сохраняет файл счёта → в заявке появляются
   `invoice_path`, `invoice_total`, `payment_status = 'debt'`, цены позиций.
   Там же проверяется **доставка**: поле «🚚 Стоимость доставки» входит в итог
   счёта (14 000 материалы + 1 500 доставка = 15 500) и сохраняется отдельной
   позицией заявки (`orders.js` → `saveDeliveryItem()`, `CONFIG.DELIVERY_ITEM`),
   подставляется в окно счёта при повторном открытии, а очистка поля удаляет
   строку из заявки и из итога; повторное сохранение не создаёт вторую строку.
   Отдельно прогоняется выбор **«🏢 Доставка компании»**: строка
   переименовывается в «Доставка компании», в счёт поставщика сумма не входит
   (`invoice_total` = 14 000, `total_sum` = 14 800), в окне счёта появляется
   подсказка «вне счёта», выбранный вид восстанавливается при повторном открытии,
   а при возврате к «доставке поставщика» та же строка переименовывается обратно
   (счёт снова 15 500, второй строки не появляется). Своя доставка из подотчёта
   оставляет в базе `cash_operation` с `source = 'own_delivery'`; при возврате на
   «доставку поставщика» этот расход удаляется — мок отдаёт расходам `id` и
   фильтрует их по `order_id` и `source`, как настоящая база, иначе приложение
   не могло бы убрать лишний расход, и проверка была бы фиктивной;
2. **«🚚 Доставлено на объект»** → `status = 'delivered'`, `delivered_at`,
   позиции (включая доставку) уходят в «Реестр материалов» со статусом
   «Ожидает оплаты», при этом подотчёт снабженца **не** меняется (безнал фирмы).
   В реестре доставка показана отдельной строкой с категорией «🚚 Доставка», и
   фильтр «Категория → 🚚 Доставка» оставляет в таблице только её. Вид доставки
   решает колонка `order_items.delivery_kind` (v2.5.0), поэтому прогон проверяет,
   что одного переименования строки НЕ достаточно (статус остаётся «Ожидает
   оплаты»), и только после простановки признака `'company'` у строки появляется
   «🏢 Вне счёта» — долга перед поставщиком по ней нет (сумма в счёт не входила);
3. **Финансист** видит счёт в блоке «🧾 Счета на материалы» (меню
   «⏳ Ожидают оплату / ✅ Оплаченные»). Карточка очереди показывает СТАТУС
   «⏳ Ожидает оплату», а не кнопку оплаты (раньше там стояла зелёная кнопка
   «✅ Оплачено», и список читался как «эти счета уже оплачены»): клик по
   заявке открывает окно подробностей (`#material-invoice-detail-modal`) —
   суммы по счёту и по заявке, объект, раздел, поставщик, даты и файл счёта, —
   и **оплата идёт кнопкой из этого окна** → `paid_at`, `paid_by_employee_id`,
   позиции становятся «Оплачено», окно закрывается, счёт уходит из очереди в
   историю «✅ Оплаченные» (дата оплаты и кто оплатил), а подотчёт
   финансиста остаётся прежним. Там же проверяется выгрузка **по фильтру**:
   у истории есть «📅 Всё время / Этот месяц / Прошлый месяц», кнопка
   «📥 Excel» выгружает ровно видимые строки (файл `.xlsx`), а по пустому
   фильтру выгрузки не происходит;
4. **Директор** пополняет подотчёт финансиста → операция с
   `source = 'financier_topup'`, ведомость пополнений (строки, итог,
   количество) и выгрузка в Excel;
5. **Настройки**: переключение языка (RU/UK, меняется `<html lang>` и
   переводы в уже открытой вкладке) и цветовой схемы (переменные
   `--brand*` и перекраска классов Tailwind).

Отдельно прогон стережёт пять регрессий по жалобам с боевого приложения:

* карточка «Новой» заявки **не** показывает «Оплачено» (раньше позиции
  создавались сразу со `payment_status = 'paid'`);
* в окне «🚚 Доставлено на объект» строки позиций подписаны по выбору
  «кто платит»: фирма → «Ожидает оплаты», подотчёт снабженца → «Оплачено»
  (раньше там стоял статичный текст с обоими вариантами);
* после доставки карточка честно показывает «Ожидает оплаты», пока
  финансист не отметил счёт;
* **оплата счёта — не «случайная кнопка».** В очереди «⏳ Ожидают оплату»
  карточка подписана статусом «Ожидает оплату», а оплата идёт кнопкой из окна
  подробностей: прогон открывает окно кликом по заявке и закрывает долг именно
  этой кнопкой (прямой вызов `markMaterialInvoicePaid()` прошёл бы мимо
  интерфейса, поэтому проверка была бы фиктивной), а после оплаты убеждается,
  что окно закрылось;
* **«база не обновлена»**. В конце прогона мок отвечает так же, как PostgREST
  на базе с наполовину применённой миграцией: чтение `orders` с отсутствующей
  колонкой → `42703`, запись → `PGRST204`. Проверяется, что сотрудник видит
  объяснение, а не пустые списки:
  * раздел «Снабжение» — жёлтая плашка `#orders-warning`, если список заявок не
    загрузился (мок отдаёт `PGRST200`: сломана связь внешнего ключа);
  * «Сохранить счёт» — тост с колонкой `payment_status` и файлом
    `database/migrate-v2.4.sql` (та самая жалоба «не отправляются счета
    финансисту»);
  * «Реестр материалов» — плашка `#registry-warning`;
  * блок «🧾 Счета на материалы» на рабочем столе финансиста — «Не удалось
    загрузить счета: … migrate-v2.4.sql»;
  * **«заявка не закрывается»** — мок отвечает как база со старым
    CHECK-ограничением (`23514`: `new row for relation "orders" violates check
    constraint "orders_status_check"`), и тост обязан быть русским, называть
    ограничение `orders_status_check` и файл `migrate-v2.4.sql`, а английская
    строка Postgres — не показываться (проверяет `js/database.js` →
    `explainError()`).
  * **доставка не дублируется и её можно убрать.** Мок теперь по-настоящему
    удаляет строки по `DELETE` (раньше отвечал пустым `204`): повторное
    сохранение счёта обновляет строку «🚚 Доставка», а пустое поле удаляет её —
    в заявке остаётся ровно одна строка доставки, и итог счёта возвращается к
    сумме материалов. Так прогон ловит ошибку «доставку вписали дважды — в
    реестре и у финансиста сумма больше счёта».

`fin-fix-check.mjs` с `FLOW=order` дополнительно проверяет, что в позиции
создаваемой заявки вообще не пишется `payment_status`.
