# Проверочные прогоны (автотесты приложения)

Эти файлы — не часть приложения. Это автопроверки. Большинство поднимает
локальный сервер, подменяет Supabase моком, открывает приложение в **настоящем
Chrome** и убеждается, что интерфейс делает именно то, что должен (какие строки
пишутся в базу, какие операции создаются, что видит каждая роль). Пять прогонов
работают вообще без браузера и без зависимостей: `migration-check.mjs`,
`i18n-check.mjs`, `vat-check.mjs`, `schema-live-check.mjs` (только Node; последнему
нужна ещё сеть — он спрашивает живую базу) и `migration-run-check.mjs` (нужен пакет
`@electric-sql/pglite`, без него прогон пропускается).

Приложение от этих файлов не зависит: папка `tools/` не публикуется на
хостинге (см. `.vercelignore`).

## Что нужно для запуска

* **Node.js 18+** (проверки используют `fetch` и `WebSocket`); для
  `node --check js/*.js` удобнее Node 22+ — он сам распознаёт ES-модули;
* **Google Chrome** (обычная установка в `C:\Program Files\Google\Chrome\...`) —
  только для браузерных прогонов.

Дополнительные пакеты ставить не нужно — только стандартная библиотека Node
(исключение — `migration-run-check.mjs`, см. выше).

## Как запускать

Из папки `tools/checks`:

```powershell
node invoice-check.mjs         # счёт → доставка → реестр → оплата (меню «ожидают / оплаченные», Excel)
node fin-workflow-check.mjs    # заявки финансов (прораб → директор → финансист) и фильтры рабочего экрана
$env:SCENARIO='A'; node fin-fix-check.mjs              # заявка финансов, сценарий A (успех)
$env:FLOW='order'; node fin-fix-check.mjs              # то же для заявки на материалы

node migration-check.mjs       # статические проверки SQL миграций v2.4.0, v2.5.0, v2.6.0 (браузер не нужен)
node migration-run-check.mjs   # миграции v2.4.0 и v2.6.0 в настоящем Postgres (нужен пакет @electric-sql/pglite)
node i18n-check.mjs            # словарь языков: ключи RU/UK, подстановки, разметка (браузер не нужен)
node vat-check.mjs             # НДС не начисляется дважды и своя доставка — расход объекта (браузер не нужен)
node schema-live-check.mjs     # схема БОЕВОЙ базы: колонки миграций v2.4.0/v2.5.0 на месте? (нужна сеть)
```

`migration-check.mjs` — обычная проверка без браузера и без зависимостей: она
сверяет `database/migrate-v2.4.sql` и `database/schema.sql`, следит, чтобы
колонки добавлялись только с `if not exists` и в защищённых блоках, ищет в SQL
типографские кавычки и невидимые пробелы (из-за них команда молча ломается при
копировании из документа) и проверяет, что миграция обновляет CHECK-ограничение
`orders_status_check` под статус `delivered`. Отдельным блоком стережётся
миграция **v2.5.0** (`database/migrate-v2.5.sql` — НДС и своя доставка): её
колонки, защищённые блоки, самопроверка `ok / MISSING`, `notify pgrst` и
заполнение вида доставки у старых строк. Типографские кавычки ищутся и внутри
строковых литералов — поэтому в боевом SQL подписи пишутся обычными кавычками
(`у строк "Доставка компании"`), а «ёлочки» остаются только в комментариях: файл
копируют в SQL Editor руками. Тем же набором проверок стережётся
и служебный файл `database/fix-orders-status-check.sql`, а отдельным блоком — **v2.6.0**
(`database/migrate-v2.6.sql`: архив заявок на финансы, правка CHECK-ограничения
`cash_requests_status_check`, ни одного `add column`), включая сверку шести статусов с
`js/modules/cash-requests.js`. Возвращает код 1, если есть замечания.

`migration-run-check.mjs` делает то же самое «по-настоящему»: поднимает Postgres
в памяти (PGlite) в состоянии боевой базы «миграция применилась наполовину»
(включая старое CHECK-ограничение `orders_status_check` без статуса
`delivered`), выполняет файл миграции и проверяет, что колонок стало 8,
`payment_status` получил `default 'paid'`, самопроверка печатает 8 строк `ok`,
**до миграции заявку нельзя перевести в `delivered` (та самая боевая ошибка),
а после — можно**, проверка ограничения печатает `ok`, повторный запуск
безопасен и при сбое `alter table` скрипт всё равно доходит до конца, сообщая
`MISSING`. Отдельно так же проверяется служебный файл
`database/fix-orders-status-check.sql`. Второй сценарий — миграция **v2.6.0**
(`database/migrate-v2.6.sql`): на `cash_requests` ставится боевое ограничение без `archived` и
`revision`, и прогон убеждается, что «📥 В архив» и «✏️ На доработку» до миграции падают именно с
боевой ошибкой `cash_requests_status_check`, что самопроверка файла до правки честно печатает
`MISSING`, а после — шесть строк `ok`, что ограничение разрешает все шесть статусов кода,
повторный запуск безопасен и колонок файл не добавляет. Пакет ставится только для этого прогона
(`npm install @electric-sql/pglite`); нет пакета — прогон пропускается.

`i18n-check.mjs` — тоже без браузера и без зависимостей: он сверяет словарь
языков `js/i18n.js` с тем, что просит интерфейс. Проверяет, что каждый ключ из
`t('...')` в `js/modules/*.js` и из `data-i18n="..."` в `index.html` есть и в
русском, и в украинском словаре (`t()` без ключа возвращает сам ключ — сотрудник
увидел бы «order.paymentPending» вместо «⏳ Ожидает оплаты»), что наборы ключей
RU и UK совпадают, что подстановки `{number}` из вызовов `t('ключ', { ... })`
есть в текстах обоих языков, что надпись рядом с `data-i18n` в разметке не
разошлась со словарём (иначе при переключении RU → UK → RU текст «прыгает»),
и что в словаре нет ключей-дублей. Неиспользуемые ключи печатаются как
примечание `note` — это не ошибка. Прогон уже нашёл расхождение: подсказка
`order.invoiceHint` в разметке дописалась словами «а заявка перейдёт в «Ожидает
оплаты»», а в словаре осталась старая версия — то есть на украинском эта часть
фразы пропадала.

`vat-check.mjs` — тоже без браузера и без зависимостей, но в отличие от остальных
он **загружает настоящий код приложения** (`js/utils.js` и `js/config.js` — их
функции вызываются напрямую) и читает текст `index.html`, `js/modules/orders.js`,
`js/i18n.js` и `database/migrate-v2.5.sql`, сверяя их между собой. Зачем:
в v2.5.0 у счёта появились режим цены (`orders.invoice_price_mode`), ставка НДС и
своя доставка, и две ошибки в этой логике тихие — сумма выглядит правдоподобно,
но неверна. Прогон стережёт обе:

1. **налог не начисляется дважды.** Если цены уже с НДС, `utils.calcVat()`
   обязан ВЫДЕЛИТЬ налог из суммы (`base + vat === total`, итог не растёт);
   если без НДС — добавить его сверху ровно один раз. Отдельно проверяется, что
   повторное сохранение счёта ничего не меняет (налог не «накапливается»),
   ставка 0 % не добавляет ничего, `vatFromTotal()` именно выделяет налог из
   готовой суммы, `normalizeVatRate()` не пропускает мусор и минус, а режим по
   умолчанию — безопасный («цены уже с ПДВ»). Суммы проверяются до копейки на
   наборе из нескольких сумм и ставок (0 / 7 / 20 / 20,5 %), потому что ошибка
   вылезает именно на округлении;
2. **своя доставка — внутренний расход, а не деньги поставщика.** Строка
   «Доставка компании» не входит в счёт поставщика (и её НДС тоже) и показывается
   как «🏢 Вне счёта». Если её оплатили из подотчёта, `orders.js` создаёт
   `cash_operation` с `source = 'own_delivery'`, и тогда строка заявки из денег
   исключается (`utils.isOwnDeliveryCovered()`) — иначе сумма попала бы в план-факт,
   реестр и «Доп. расходы» дважды: строкой заявки и расходом подотчёта. Прогон
   проверяет и обратное: доставка поставщика из денег НЕ исключается (она уже
   внутри счёта), у неоплаченной своей доставки остаётся «🏢 Вне счёта», а обычная
   позиция заявки под эту проверку не попадает. Отдельно сверяется, что общая
   проверка живёт в одном месте (`js/utils.js`), ею пользуются `cash.js`,
   `dashboard.js` и `registry.js`, а вид доставки читается из колонки
   `delivery_kind` (со старым запасным вариантом «по имени строки» для строк,
   созданных до v2.5.0);
3. **разметка окна счёта совпадает с `CONFIG`:** два режима цены и оба вида
   доставки в `index.html` — ровно те значения, что в `CONFIG.VAT.MODE` и
   `CONFIG.DELIVERY_ITEM.TYPE`; у поля ставки границы 0…100 и значение по
   умолчанию из конфига; варианты «чем списываем свою доставку» совпадают с
   `CONFIG.DELIVERY_ITEM.CHARGE`; и главное — **в разметке нет галочки «начислить
   НДС»** (снабженец выбирает режим цены, а не второе начисление);
4. **налог считается в одном месте:** в коде нет «ручного» `×1,2`, суммы позиций
   сохраняются уже с НДС (`price_with_vat`), расшифровка «в т.ч. ПДВ» — это
   выделение налога, режим и ставка сохраняются вместе со счётом;
5. **база и словарь:** все 12 колонок v2.5.0 (`orders`, `order_items`,
   `cash_operations`) перечислены в самопроверке миграции, описаны в
   `schema.sql`, значения в базе совпадают с `CONFIG`, старым строкам доставки
   проставляется `delivery_kind`, а подписи НДС и своей доставки есть и в
   русском, и в украинском словаре;
6. **подсказка при непройденной миграции называет НУЖНЫЙ файл.** Прогон
   вызывает настоящий `js/database.js` → `explainError()`: колонки НДС и своей
   доставки (10 имён из 12 колонок миграции) обязаны вести к
   `database/migrate-v2.5.sql`, колонки v2.4.0 (`payment_status`, `delivered_at`,
   `invoice_total`…) — к `database/migrate-v2.4.sql`, а незнакомая колонка — к
   базовой v2.4.0 (выдумывать несуществующий файл нельзя: он проверяется и на
   диске). Список колонок в коде сверяется со списком миграции, чтобы они не
   разошлись. Раньше на любую отсутствующую колонку приложение отвечало
   «примените migrate-v2.4.sql», и администратор запускал не тот файл, получая
   ту же ошибку второй раз.

   Отдельно проверяется подсказка в **консоли** (её администратор читает, когда
   сам ищет причину): она обязана называть версию нужной миграции — «база
   не обновлена под v2.4.0» для `payment_status`, а не версию приложения
   («под v2.5.0»), иначе подсказка снова уводит не к тому файлу.

Проверено, что прогон действительно ловит поломку: если в `utils.js` заменить
выделение налога на начисление сверху, падают сразу 4 проверки — «цены уже с
ПДВ», «пересохранение», «base + vat === total» и «vatFromTotal». Если в
`js/database.js` заставить `migrationForColumn()` всегда возвращать v2.4.0,
падает проверка блока 5б «отсутствие колонки v2.5.0 ведёт к migrate-v2.5.sql».
Если вернуть в консольную подсказку версию приложения
(`CONFIG.APP.VERSION` вместо `migration.version`), падает проверка
«консоль называет версию нужной миграции (v2.4.0), а не версию приложения».

`schema-live-check.mjs` — единственный прогон, который смотрит не в файлы, а в **живую базу**.
Повод: приложение и база обновляются отдельно, и сотрудник при сохранении счёта читает «База
данных не обновлена: в таблице «orders» нет колонки «invoice_price_mode». Примените
`database/migrate-v2.5.sql`». Это не баг интерфейса, а неприменённая миграция — но увидеть это
можно только на боевой базе. Прогон берёт адрес и anon-ключ из `js/config.js` (те же, что у
приложения) и спрашивает базу **тем же способом**, что и приложение: выгружает одну колонку с
`limit=1` через `/rest/v1/`. Колонка есть — `ok`, PostgREST ответил `42703` или `PGRST204` —
`FAIL` с именем файла миграции. В конце — блок «ЧТО ДЕЛАТЬ»: какие колонки не на месте, каким
файлом их добавить и что проверить после (для «наполовину применённой» миграции — отдельная
строка «миграция применена НАПОЛОВИНУ, запустите файл ещё раз целиком»).

Список колонок не выдуман: он читается из самопроверок `database/migrate-v2.4.sql` (8 колонок)
и `database/migrate-v2.5.sql` (12 колонок), поэтому разойтись с миграциями прогон не может —
если в SQL добавили колонку, он напомнит про неё. Запись в базу не выполняется ни при каком
исходе (только `select ... limit=1`), поэтому запускать на боевой базе можно в любой момент.
Другую базу можно проверить без правки файла: `SUPABASE_URL` и `SUPABASE_ANON_KEY` в переменных
окружения. Ключ в отчёт не попадает — печатается только хост.

Миграция **v2.6.0** этим прогоном не проверяется, и это не упущение: она колонок не добавляет, а
список допустимых статусов (`cash_requests_status_check`) через `/rest/v1/` не виден. Состояние
ограничения смотрят запросом в SQL Editor (раздел «Как применить `migrate-v2.6.sql`» в
`database/README.md`) или прогоном `migration-run-check.mjs`, который выполняет файл в настоящем
Postgres.

Пути можно переопределить переменными окружения:

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `APP_ROOT` | корень репозитория (на две папки выше) | если приложение лежит в другой папке |
| `CHROME_PATH` | `C:/Program Files/Google/Chrome/Application/chrome.exe` | если Chrome установлен иначе |
| `SCENARIO` | `A` | сценарий ответа базы в `fin-fix-check.mjs`: `A` — запись принята, `B` — RLS не пускает (401), `C` — 201 без тела |
| `FLOW` | `finance` | тип заявки в `fin-fix-check.mjs`: `finance` — заявка на деньги, `order` — на материалы |
| `SUPABASE_URL` | `CONFIG.SUPABASE_URL` из `js/config.js` | `schema-live-check.mjs`: проверить другую базу (например, тестовый проект) |
| `SUPABASE_ANON_KEY` | `CONFIG.SUPABASE_ANON_KEY` из `js/config.js` | то же: anon-ключ к этой базе |

## Куда смотреть результат

Каждый прогон печатает отчёт в консоль (`  ok  ` по каждой проверке) и
дополнительно кладёт его в текстовый файл в `%TEMP%\rsk-fin\`:

* `invoice-check.txt`, `fin-workflow.txt`, `fin-fix-finance.txt`, `fin-fix-order.txt`,
  `migration-check.txt`, `migration-run-check.txt`, `i18n-check.txt`,
  `vat-check.txt`, `schema-live-check.txt`.

В конце отчёта — строка «ВСЁ ВЕРНО…» или список непрошедших проверок, а также
фактическое состояние мок-базы (заявки, операции, балансы) и ошибки консоли
браузера. Если в консоли появились исключения, прогон считается неуспешным —
это ловит сломанные обработчики, которые не видны по тексту на экране.
Все прогоны возвращают **код 1**, если есть непройденные проверки (и 0, если всё
хорошо) — можно ставить в автоматику, не читая отчёт глазами. Исключение —
`migration-run-check.mjs` без пакета `@electric-sql/pglite`: он печатает
«прогон пропущен» и возвращает 0.

## Что именно проверяет `invoice-check.mjs`

Цепочка закупки материалов, ради которой прогон и написан:

1. **Снабженец** создаёт заявку, открывает «🧾 Счёт от поставщика», заполняет
   поставщика и цены, сохраняет файл счёта → в заявке появляются
   `invoice_path`, `invoice_total`, `payment_status = 'debt'`, цены позиций.
   Там же проверяется **доставка**: поле «🚚 Стоимость доставки» входит в итог
   счёта (14 000 материалы + 1 500 доставка = 15 500) и сохраняется отдельной
   позицией заявки (`orders.js` → `saveDeliveryItem()`, `CONFIG.DELIVERY_ITEM`),
   подставляется в окно счёта при повторном открытии, а очистка поля удаляет
   строку из заявки и из итога; повторное сохранение не создаёт вторую строку.
   Отдельно прогоняется выбор **«🏢 Доставка компании»**: строка
   переименовывается в «Доставка компании», в счёт поставщика сумма не входит
   (`invoice_total` = 14 000, `total_sum` = 14 800), в окне счёта появляется
   подсказка «вне счёта», выбранный вид восстанавливается при повторном открытии,
   а при возврате к «доставке поставщика» та же строка переименовывается обратно
   (счёт снова 15 500, второй строки не появляется). Своя доставка из подотчёта
   оставляет в базе `cash_operation` с `source = 'own_delivery'`; при возврате на
   «доставку поставщика» этот расход удаляется — мок отдаёт расходам `id` и
   фильтрует их по `order_id` и `source`, как настоящая база, иначе приложение
   не могло бы убрать лишний расход, и проверка была бы фиктивной;
2. **«🚚 Доставлено на объект»** → `status = 'delivered'`, `delivered_at`,
   позиции (включая доставку) уходят в «Реестр материалов» со статусом
   «Ожидает оплаты», при этом подотчёт снабженца **не** меняется (безнал фирмы).
   В реестре доставка показана отдельной строкой с категорией «🚚 Доставка», и
   фильтр «Категория → 🚚 Доставка» оставляет в таблице только её. Вид доставки
   решает колонка `order_items.delivery_kind` (v2.5.0), поэтому прогон проверяет,
   что одного переименования строки НЕ достаточно (статус остаётся «Ожидает
   оплаты»), и только после простановки признака `'company'` у строки появляется
   «🏢 Вне счёта» — долга перед поставщиком по ней нет (сумма в счёт не входила);
3. **Финансист** видит счёт в блоке «🧾 Счета на материалы» (меню
   «⏳ Ожидают оплату / ✅ Оплаченные»). Карточка очереди показывает СТАТУС
   «⏳ Ожидает оплату», а не кнопку оплаты (раньше там стояла зелёная кнопка
   «✅ Оплачено», и список читался как «эти счета уже оплачены»): клик по
   заявке открывает окно подробностей (`#material-invoice-detail-modal`) —
   суммы по счёту и по заявке, объект, раздел, поставщик, даты и файл счёта, —
   и **оплата идёт кнопкой из этого окна** → `paid_at`, `paid_by_employee_id`,
   позиции становятся «Оплачено», окно закрывается, счёт уходит из очереди в
   историю «✅ Оплаченные» (дата оплаты и кто оплатил), а подотчёт
   финансиста остаётся прежним. Там же проверяется выгрузка **по фильтру**:
   у истории есть «📅 Всё время / Этот месяц / Прошлый месяц», кнопка
   «📥 Excel» выгружает ровно видимые строки (файл `.xlsx`), а по пустому
   фильтру выгрузки не происходит;
4. **Директор** пополняет подотчёт финансиста → операция с
   `source = 'financier_topup'`, ведомость пополнений (строки, итог,
   количество) и выгрузка в Excel;
5. **Настройки**: переключение языка (RU/UK, меняется `<html lang>` и
   переводы в уже открытой вкладке) и цветовой схемы (переменные
   `--brand*` и перекраска классов Tailwind).

Отдельно прогон стережёт пять регрессий по жалобам с боевого приложения:

* карточка «Новой» заявки **не** показывает «Оплачено» (раньше позиции
  создавались сразу со `payment_status = 'paid'`);
* в окне «🚚 Доставлено на объект» строки позиций подписаны по выбору
  «кто платит»: фирма → «Ожидает оплаты», подотчёт снабженца → «Оплачено»
  (раньше там стоял статичный текст с обоими вариантами);
* после доставки карточка честно показывает «Ожидает оплаты», пока
  финансист не отметил счёт;
* **оплата счёта — не «случайная кнопка».** В очереди «⏳ Ожидают оплату»
  карточка подписана статусом «Ожидает оплату», а оплата идёт кнопкой из окна
  подробностей: прогон открывает окно кликом по заявке и закрывает долг именно
  этой кнопкой (прямой вызов `markMaterialInvoicePaid()` прошёл бы мимо
  интерфейса, поэтому проверка была бы фиктивной), а после оплаты убеждается,
  что окно закрылось;
* **«база не обновлена»**. В конце прогона мок отвечает так же, как PostgREST
  на базе с наполовину применённой миграцией: чтение `orders` с отсутствующей
  колонкой → `42703`, запись → `PGRST204`. Проверяется, что сотрудник видит
  объяснение, а не пустые списки:
  * раздел «Снабжение» — жёлтая плашка `#orders-warning`, если список заявок не
    загрузился (мок отдаёт `PGRST200`: сломана связь внешнего ключа);
  * «Сохранить счёт» — тост с колонкой `payment_status` и файлом
    `database/migrate-v2.4.sql` (та самая жалоба «не отправляются счета
    финансисту»);
  * «Реестр материалов» — плашка `#registry-warning`;
  * блок «🧾 Счета на материалы» на рабочем столе финансиста — «Не удалось
    загрузить счета: … migrate-v2.4.sql»;
  * **«заявка не закрывается»** — мок отвечает как база со старым
    CHECK-ограничением (`23514`: `new row for relation "orders" violates check
    constraint "orders_status_check"`), и тост обязан быть русским, называть
    ограничение `orders_status_check` и файл `migrate-v2.4.sql`, а английская
    строка Postgres — не показываться (проверяет `js/database.js` →
    `explainError()`).
  * **доставка не дублируется и её можно убрать.** Мок теперь по-настоящему
    удаляет строки по `DELETE` (раньше отвечал пустым `204`): повторное
    сохранение счёта обновляет строку «🚚 Доставка», а пустое поле удаляет её —
    в заявке остаётся ровно одна строка доставки, и итог счёта возвращается к
    сумме материалов. Так прогон ловит ошибку «доставку вписали дважды — в
    реестре и у финансиста сумма больше счёта».

`fin-fix-check.mjs` с `FLOW=order` дополнительно проверяет, что в позиции
создаваемой заявки вообще не пишется `payment_status`.
